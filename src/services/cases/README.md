# services/cases/

The biggest, most central folder — case data access, LIS-vs-Orchestration routing, and production-migration planning.

**Pattern:** See PRODUCTION_MIGRATION.md — this folder deliberately does NOT follow the simple interface/mock/firestore triplet; read that doc first.

## Files

- **`ICaseService.ts`** — The contract any case data source must satisfy (mock, Firestore, HL7 FHIR, or direct LIS DB). `updateCase` now takes an optional third `expectedVersion?: number` parameter (added for the Case Hydration & Optimistic Concurrency Control spec) — omitted entirely, every existing call site keeps today's unconditional-write behavior; provided, the implementation must perform a real compare-and-swap and throw `ConcurrencyConflictError` on a mismatch. Additive, not a breaking change.
- **`ConcurrencyConflictError.ts`** — New. The real 409-equivalent contract every case service throws on a genuine version mismatch — carries `caseId`/`expectedVersion`/`actualVersion` so a catcher can build a real reconciliation UI rather than a generic error message. `CaseRouter.ts` specifically preserves and rethrows this type rather than swallowing it into a generic error (see its own entry below) — losing that distinction here would have made every downstream conflict-handling fix pointless.
- **`CaseRouter.ts`** — THE FACADE — routes between LIS cases (S26- prefix) and Orchestration cases (O26- prefix). Production-critical, explicitly marked 'keep' in PRODUCTION_MIGRATION.md. **Real fix:** `updateCase`'s catch block used to discard whatever error the underlying service threw and replace it with a generic one (`catch { throw new Error(...) }`, not even capturing the original) — meaning a `ConcurrencyConflictError` thrown by any case service would have been silently lost before ever reaching a caller. Now passes `expectedVersion` through and explicitly preserves/rethrows `ConcurrencyConflictError` by type.
- **`casePoolAssignmentService.ts`** — (renamed from caseRoutingService.ts) Automatic case-POOL/subspecialty routing when no LIS assignment exists — a genuinely DIFFERENT concern from CaseRouter.ts (business logic, not data-source selection). Called from HL7 inbound handler, LIS polling, and the manual 'Route to Pool' action.
- **`AuditLogger.ts`** — DSPT/GDPR-compliant structured access logging, partitioned per data source for medico-legal clarity. **Real fix, found via a direct question about whether these events showed up on the System Audit page — they didn't:** this previously only did `console.debug()` in dev mode, completely disconnected from `services/auditlog/` — the actual store `AuditLogPage.tsx` reads from. Every `case.read`/`case.write`/`case.write.conflict` event logged by any case service was invisible to any real user. Now genuinely writes into the same real audit store as every other audit trail in this app, fire-and-forget (an audit write failing must never fail the case operation it describes). Also added a real, distinct `case.write.conflict` event type — separate from a generic `case.write` failure, so a real audit review can tell "someone else won a race" apart from "the write actually broke."
- **`FHIRCaseService.ts`** — Production NHS HL7 FHIR R4 implementation — deliberate scaffolding, not yet wired in. Full resource-mapping table and go-live TODO list in its own header.
- **`FirestoreCaseService.ts`** — (casing fixed July 2026 — was firestoreCaseService.ts, mismatched PRODUCTION_MIGRATION.md's documented name, would have broken on a case-sensitive/Linux deploy) Production Orchestration-case data source. **Real fix:** `updateCase` now performs the actual optimistic-concurrency compare-and-swap inside a genuine Firestore `runTransaction` — reads the current version, compares, throws `ConcurrencyConflictError` on mismatch, writes and increments atomically on match. Not a two-step check-then-write (which would itself race) — a real transaction.
- **`FirestoreCaseService.test.ts`** — Real tests against a mocked Firestore SDK (the existing pattern this file already used) — extended with real coverage of the version compare-and-swap: matching version succeeds, mismatched version throws and never writes, a legacy case with no version field yet is treated as version 0 rather than crashing, a case that doesn't exist yet is treated as version 0 inside the transaction.
- **`caseFilterUtils.ts`** — Shared case-filtering pipeline — extracted specifically to stop mockCaseService.ts and mockOrchestratorCaseService.ts's filter logic from drifting apart, the same class of bug this codebase has hit and fixed repeatedly (see its own header comment for the pattern list).
- **`mockCaseService.ts`** — MASSIVE (4,000+ lines) — the real, active LIS-mode mock data source. Marked for deletion at production go-live per PRODUCTION_MIGRATION.md Step 4. **Real fix:** `updateCase` now has the same real version compare-and-swap as `FirestoreCaseService.ts` — single-threaded JS means a synchronous check-then-write is genuinely atomic here, no transaction needed the way Firestore requires one.
- **`mockOrchestratorCaseService.ts`** — Large — the real, active Orchestration-mode mock data source. Also marked for deletion at go-live. Same real version compare-and-swap fix as `mockCaseService.ts` — this is the service that actually backs Orchestration-mode case writes (`orchSections` etc.), confirmed via `CaseRouter`'s real constructor wiring (`new CaseRouter(mockCaseService, mockOrchestratorCaseService)`), so it needed the identical fix independently, not automatically covered by fixing the LIS-mode service alone.
- **`mockCaseServiceConcurrency.test.ts`** — New. Real tests run against BOTH mock services via `describe.each` (not mocked-away logic — actual writes, actual conflicts, actual version increments), covering: unconditional writes when no `expectedVersion` is given, a matching version succeeding, a mismatched version throwing and never landing, the thrown error carrying the real expected/actual versions, and that a conflict on one case never affects an unrelated case (no accidental global lock).
- ~~**`concurrencyCheck.ts`**~~ — Deleted. An earlier, superseded two-step "check then write" approach (a separate read to check staleness, then a second write) that had a real TOCTOU race window between the check and the write — something could change in between. Replaced by the atomic compare-and-swap built directly into `updateCase` itself; no consumers remained once `SynopticReportPage.tsx` was migrated to the real version, so removed rather than left as dead code.

## Notes

- READ PRODUCTION_MIGRATION.md FIRST when working in this folder — it's a genuinely detailed, real go-live runbook (SMART on FHIR auth options, NHS DSPT compliance by jurisdiction, GDPR Art 25 data-minimization reasoning, Caldicott Guardian approval, Firestore UK/EU residency).
- The O26-/S26- accession prefix convention (Orchestration vs LIS) is central to how this whole folder works — see CaseRouter.ts.
- **Real optimistic concurrency now exists end-to-end** (Case Hydration & Optimistic Concurrency Control spec) — schema (`Case.version` in `types/case/Case.ts`), the real compare-and-swap in all three writable services above, `ConcurrencyConflictError` as the shared contract, and `CaseRouter.ts` correctly propagating it. `firestore.rules` (repo root) enforces the same version check server-side, emulator-verified with 22 real tests. What's NOT done: only `SynopticReportPage.tsx`'s actual write call sites have been wired to pass `expectedVersion` and handle the error — every OTHER file that might call `caseRouter.updateCase()` still needs auditing individually before this protection is meaningful everywhere it's called from, not just where it's technically available.
