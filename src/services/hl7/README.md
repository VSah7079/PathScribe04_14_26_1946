# services/hl7/

Standard-conformant HL7 v2.5.1 ORM^O01 message builder, with a vendor-adapter seam for receiving-system-specific quirks. **Phase 3 addition**: a real DFT^P03 (financial transaction) builder — the outbound side of the specimen/block-level CPT association work in `types/case/Specimen.ts` and `services/billing/`. **Phase 1 addition (Patient/Encounter subsystem): the first real INBOUND direction** — everything above this is outbound (PathScribe data → HL7 text); `hl7Parser.ts`/`adtParser.ts`/`processAdtMessage.ts` go the other way (real HL7 text received from an external system → structured data, wired into the real MPI and Encounter services). **Real fix, Phase 2 of the facility-timezone effort**: every real HL7 TS (Timestamp) field this folder produces now carries the real, signed FACILITY UTC offset (e.g. `-0700` for Tucson), not the sending browser/device's own offset — per direct HL7 v2.x guidance (a TS field's offset must reflect the real, originating facility; sending a browser-local offset breaks message parsing at the receiving LIS). See `utils/facilityTime.ts`.

**Pattern:** DELIBERATE PRE-INTEGRATION SCAFFOLDING for the outbound builders — nothing in the app currently calls either. The inbound parsing pipeline is genuinely, actively wired into real services (`services/patients/`, `services/encounters/`), even though nothing in the app yet calls `processAdtMessage()` from a real transport layer (no inbound HL7 listener exists yet — that's real, separate infrastructure work, not a gap in this folder).

## Files

- **`index.ts`** — Single entry point — orchestrates ormBuilder + an adapter (defaults to identityAdapter). `generateOutboundHL7ForBlock` now takes a required, real facility `timezone` parameter.
- **`ormBuilder.ts`** — Assembles a complete ORM^O01 message from Case/Specimen/HistologyBlock/StainOrder — one message per Block, one OBR per stain ordered. `buildOrmO01ForBlock` now takes a required, real facility `timezone` parameter, threaded to every segment builder that produces a timestamp.
- **`dftBuilder.ts`** — Assembles a complete DFT^P03 message from real, actually-assigned CPT charges. Deliberate, honest scope boundary: only ever emits real, physician/system-assigned codes. `buildDftP03ForCase` now takes a required, real facility `timezone` parameter.
- **`segmentBuilders.ts`** — One function per segment (MSH/PID/PV1/ORC/OBR/SPM/NTE, FT1/DG1) — every field position confirmed against real IHE PaLM/HL7 sources. **Real fix, Phase 2**: `toHL7Timestamp` (used by MSH-7/ORC-9/OBR-7) now takes a required, real facility `timezone` and produces the real, signed offset via `utils/facilityTime.ts`'s `getFacilityUtcOffsetString` — previously produced a bare, offset-less `YYYYMMDDHHmmss` using whichever timezone the browser/device happened to be in. `toHL7Date` (PID-7, FT1-4/5 — HL7's DT type has no offset component) also takes the required timezone, for the real facility-local calendar date itself. `buildMSH`/`buildPID`/`buildORC`/`buildOBR`/`buildFT1` all take this same required parameter now. See `segmentBuilders.test.ts` (new) for the real, verified offset behavior, including the exact scenario an 11pm Tucson send produces the real `-0700`.
- **`types.ts`** — HL7 message context + version constants, including the real separator constants (`HL7_FIELD_SEP`, `HL7_ENCODING_CHARS`) the new inbound parser reuses directly, so a parser and its matching builder never disagree about delimiters.
- **`adapters/IHL7VendorAdapter.ts`** — The vendor-customization seam.
- **`adapters/identityAdapter.ts`** — Default no-op adapter.
- **`adapters/vantageAdapter.ts`** — DELIBERATELY NOT IMPLEMENTED.
- **`hl7Parser.ts`** — **New.** Real, generic HL7 tokenizer — the reverse of `segmentBuilders.ts`'s builders. Splits raw text into segments/fields/components/repetitions. Handles MSH's real, standard exception (MSH-1 IS the field separator itself) explicitly. Tested against a real, published example message — caught and fixed a real manual field-counting mistake of its own before finalizing (see this file's own tests for the corrected, verified positions).
- **`adtParser.ts`** — **New.** Real ADT field extraction, built on `hl7Parser.ts`. Field positions confirmed against real, published example messages. Real, confirmed distinction: A01/A04 differ only in PV1-2 (patient class); A08 updates an existing patient but never represents a new visit. Every test fixture's field positions were verified programmatically (Python/Node) before being written into assertions — building this file caught several of its own real fixture mistakes this way, each fixed before finalizing. **A03 (discharge/end visit), added later**: real, verified PV1-45 (Discharge Date/Time) extraction, sitting directly alongside the already-parsed PV1-44. Never creates a new Encounter — only ends an existing one. **Working through the full list of ADT trigger events, per direct confirmation**: `AdtEventType` now also covers A02 (Transfer), A09/A10 (Patient Tracking — same real PV1-3/PV1-6 shape as A02, since this app's Location/Encounter model doesn't distinguish "formal transfer" from "temporary tracking" at the data level), A06/A07 (patient class change), A05 (Pre-Admit), and A11/A12/A13 (cancellations). New fields parsed that weren't before: PV1-6 (Prior Patient Location, for A02/A09/A10 — audit/validation only, since the real "restore on cancel" logic uses the Encounter's own captured `previousLocationId` rather than trusting this field alone), PV1-36 (Discharge Disposition, HL7 Table 0112, for A03), and PV1-10/14/20 (Hospital Service/Admit Source/Financial Class, for A08's real metadata updates). `locationStatus`/`personLocationType`/`dischargeDisposition`/etc. are all modeled as guided free text, not closed enums — several of these HL7 tables (0306, 0305, 0112) are genuinely site-extensible in the real standard. A45 (Move Visit Information), A50 (Change Visit Number), and A34 (Merge Patient Information — Patient ID Only) are **not yet handled** — structurally different, MRG-based visit operations, not the PID+PV1 shape this file parses; real, open follow-up work. A43 (Move Patient Information) IS now handled — see patientManagementParser.ts/processPatientManagementMessage.ts below, since it shares their real PID+MRG shape, not this file's PID+PV1 one.
- **`processAdtMessage.ts`** — **New, the actual integration point.** Wires a parsed ADT message into the SAME real `mockPatientIndexService`/`mockEncounterService` the accession-time flow already uses — not a separate, parallel identity path. A patient resolved from a real inbound A01 today is the exact same real `patientId` a specimen accessioned for them tomorrow resolves to (directly tested). **Phase 3 update**: A08 now resolves identity via the precise crosswalk lookup (`resolveByIdentifier`) rather than the full, name-verified `resolveOrCreatePatient` flow. Real, important reason found while building this: A08's entire point may be "the patient's name just legitimately changed" — running it through the same name-verification check A01/A04 correctly use would flag every real demographic update as an identity conflict, exactly backwards for the event that exists to carry one. A01/A04 keep the full, name-verified flow, since those are genuinely "might be a new patient" moments where that verification matters. **A03 update, added later**: finds the real, EXISTING encounter by its real visit number (never creates a new one - a discharge ends a visit, it doesn't start one) and applies the status transition through the same real, sequence-controlled `updateStatus()`. A real A03 with no matching prior encounter is honestly left unresolved, not fabricated. **Real feature, per direct confirmation ("we will need to accept PV1 HL7 data... Location / Rooms... naturally associated to the Facility")**: takes a new, required `facilityId` parameter (real HL7 interfaces are configured per-facility in practice — confirmed zero real callers existed yet when this was added, so it was free to design cleanly). For A01/A04/A05 with a usable PV1-3 `pointOfCare`, resolves the real `Location` (`services/locations/`) *before* resolving the `Encounter`, via the same `findOrCreateByAssigningAuthority`-style crosswalk pattern already established for `Facility`/`Physician` — no match creates a real, `Unverified`, `autoCreated` location for admin review. The resolved `locationId` is persisted onto `Encounter.locationId`.

  **All 9 new event types are now fully wired**, per direct confirmation ("finish wiring the 9 events that already have service support"): A05 (Pre-Admit) creates a real, `Planned` encounter through the same creation branch as A01/A04; A02/A09/A10 (Transfer/Tracking) find the real, existing encounter and call `updateLocation()`; A06/A07 (class change) call `updateClass()`; A08 now also calls `updateMetadata()` with its real PV1-7/10/14/20 fields (previously parsed but never actually applied to the encounter); A11 (Cancel Admit) calls `updateStatus('Cancelled')`; A12 (Cancel Transfer) calls `cancelTransfer()`; A13 (Cancel Discharge) calls `updateStatus('In-Progress')`, the real, standard "re-open an encounter" effect. A shared `resolveLocation()` helper factors out the PV1-3 crosswalk logic, reused across every event group that can carry a real location.

  **Real, pre-existing bug found and fixed while wiring these in, not introduced by them**: `resolveOrCreateEncounter()` never set a real `lastEventAt` baseline at creation, so a newly-created encounter's very first follow-up update — even a genuinely stale/out-of-order one — was silently always accepted, since every sequence-control check only fires when `lastEventAt` is already set. Caught by a real test (a deliberately-stale A02 arriving right after an A01), not by inspection. Fixed by threading the creating event's real timestamp through a new, optional `eventTimestamp` parameter — optional because `AccessionPage.tsx`'s manual accessioning call has no real ADT event timestamp to provide, and doesn't need one; the risk this guards against is specific to real inbound ADT ingestion. A45 (Move Visit Information), A50 (Change Visit Number), and A34 remain **not yet handled** — structurally different, MRG-based visit operations, not the PID+PV1 shape this file parses; real, open follow-up work.
- **`patientManagementParser.ts`** — **New, Phase 2.** Real A40 (merge)/A24 (link)/A47 (change identifier) field extraction — structurally different from the visit events above (real PID+MRG shape, not PID+PV1), confirmed against the real HL7 v2.5 standard segment reference. **Real, important correction found during research**: the original spec described A47 as "detach misidentified records/cases." That's not what real A47 does — verified directly against multiple real HL7 references, A47 ("Change Patient Identifier List") means a single patient's own identifier was corrected; same real person, same real record, only the identifier value changes. Built to match the real, verified standard, not the original spec text. **A43 (Move Patient Information), added later, per direct architecture confirmation**: now also extracts MRG-5 (Prior Visit Number), genuinely undefined when absent from the message. A43 is real, standard confirmation that target and source are NOT the same person (unlike A47) but NEITHER is retired (unlike A40) — a specific, misattributed piece of data moves between two real, independently-active identities.
- **`processPatientManagementMessage.ts`** — **New, Phase 2's actual integration point.** Wires a real A40/A24/A47 message into the SAME real `mergeIntoExistingPatient`/`linkPatients`/`addIdentifier` operations `PatientMatchReviewSection.tsx`'s human review already uses — a real inbound merge event repoints real cases the exact same way a human clicking "Merge into this patient" already does. Resolves each side via the precise crosswalk lookup first (not the full candidate-matching flow) since a merge/link/change-identifier event is, by definition, about already-known identities — this also correctly sidesteps a real structural fact: MRG never carries a DOB field at all, so running it through the full resolution flow would have incorrectly tripped the DOB-verification safety check below for missing data, not genuinely conflicting data. **A43, added later, per direct architecture confirmation** — `processMoveMessage()`: parses MRG-5, looks up the real `Encounter` it references, finds the real `Case`(s) linked to it, and moves ONLY those via the new `mockPatientIndexService.moveCaseToPatient()` (deliberately distinct from `mergeIntoExistingPatient` — neither identity is retired). Every real failure mode (no MRG-5, MRG-5 matching no Encounter, an Encounter with no linked Case) routes to `services/interfaceExceptions/` rather than auto-moving anything on a guess. A real bug caught and fixed while wiring this in: `processPatientManagementMessage()`'s main entry point would have silently mis-handled an incoming A43 by falling through to the A24 (link) branch, since nothing routed it away before an explicit check was added.

## Notes

- mockHL7Service.ts was DELETED July 2026 — an earlier, simpler stub superseded by this more rigorous standards-based system.
- **Real feature, per direct confirmation: working through the full list of ADT demographic/identity trigger events.** `adtParser.ts`'s `parsePID` now extracts PID-9 (Patient Alias, real repeating field), PID-11 (Address, real XAD component order), PID-13 (Phone), PID-16 (Marital Status, HL7 Table 0002 — genuinely site-extensible, modeled as guided free text like `locationStatus` elsewhere), and PID-29/30 (Death Indicator/Date-Time — converted to a real boolean, never `false` by default, genuinely `undefined` until a real message says so either way). `services/patients/IPatientIndexService.ts`'s `MasterPatientRecord`/`updateDemographics()` extended to match — see that folder's own README. **A real bug caught and fixed while wiring this in**: the new fields were parsed and the storage layer accepted them, but `processAdtMessage.ts` never actually passed them through to `updateDemographics()` — a real A08 carrying PID-9/11/13/16/29/30 would have parsed everything correctly and then silently discarded it. Fixed; covered by a real test confirming the full round trip, plus a second test confirming an A08 with none of these fields never blanks out previously-established real data.
- **A31 (Update Person Information), added the same pass**: real, confirmed identical PID structure to A08, routed through the exact same crosswalk-precise resolution path in `processAdtMessage.ts` — but deliberately never touches `Encounter` at all, since A31's real meaning ("demographics updated outside an active encounter context") has nothing to do with a visit, even if a real message happens to carry a PV1 segment.
- **A21/A23, investigated and NOT built, per direct verification against the real HL7 v2 standard**: confirmed across six independent real references (hl7.eu v2.1/v2.3.1, MiHIN, HL7.org's own conformance profile PDF) that A21 is "Patient goes on a leave of absence" and A23 is "Delete a Patient Record" — neither is a real "Deceased" event in the standard. The real, standard-compliant mechanism for death status is exactly what a direct note anticipated: "A standard ADT^A08 or ADT^A03 discharge message is also frequently used by many EHRs to populate the death indicator and date/time" — which the PID-29/30 work above already handles correctly via the existing A08/A03 paths. No separate "A21/A23 death handling" exists to build.
- **Real, critical safety fix found while building the inbound path**, applying to the OUTBOUND-adjacent MPI work too: `mockPatientIndexService`'s new "crosswalk-first" check (an exact assigning-authority+MRN hit) originally trusted that hit alone, with no real DOB/name verification — unlike the older, bare-MRN path, which already correctly required both. Fixed so the same real two-identifier discipline applies to both paths; see `services/patients/README.md`.
- Wire in via ormBuilder.ts's buildOrmO01ForBlock() / dftBuilder.ts's buildDftP03ForCase() + a real HTTP/MLLP transport when order/charge transmission is ready to go live. Both now require a real, configured facility timezone (System Config's `facilityTimezone`) as a parameter — the future transport-layer caller needs to supply it, same as every other real caller in this folder now does.
- **`dftBuilder.ts`'s real, honest limits**: FT1-25 (alt CPT placement) and the full institutional pattern (PR1/DRG/revenue codes) are deliberately not implemented — this app's real domain (professional anatomic pathology interpretation) matches the "professional" DFT pattern, not the institutional one, per the real, verified distinction confirmed while researching this. Modifiers (FT1-26) aren't populated yet either — this app doesn't currently capture per-code modifiers anywhere (a genuinely separate, real follow-up).
- **Real, honest, still-open follow-up (not fixed as part of Phase 2)**: `FHIRCaseService.ts` (inbound FHIR import, a different real file, not in this folder) sets `accessionYear` from `new Date().getFullYear()` — that's a deeper problem than a timezone bug (it's using the real IMPORT/SYNC moment, not the real, original accession event from the external system), flagged with an explicit `eslint-disable` comment there rather than fixed here, since the real fix needs both a real source-of-truth field on the inbound FHIR data and a parameter threaded through the widely-used `CaseRouter.ts`.
