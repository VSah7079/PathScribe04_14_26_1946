# services/ai/

The core AI provider abstraction layer. ALL AI generation in PathScribe flows through IAIProvider — nothing else in the app references a concrete provider directly.

**Pattern:** Not the interface/mock/firestore triplet pattern — this is provider abstraction (swappable providers without code changes).

**Naming:** Provider identifiers and class names here are named for their real request/response protocol shape (`structured_messages`, `chat_completions`, `model_gateway`, `structured_content`) rather than the vendor — matches `AiProviderId` in `components/Config/AI/aiProviderConfig.ts`. The admin configuration UI (`AiProviderSettings.tsx`) still shows real vendor/model names, since that's what an admin needs to see to configure a real integration; this internal naming convention doesn't extend there.

## Files

- **`IAIProvider.ts`** — The provider contract. Enables provider swapping, a mock provider for demos, audit logging at a single choke point, future per-client/subspecialty routing.
- **`AIProviderRegistry.ts`** — Resolves which concrete provider is active. **Real gap, now fixed**: previously only `structured_messages` and `mock` were actually implemented here — every other provider silently fell back to `MockProvider` with a console warning, even though `services/aiIntegration/aiProviderService.ts`'s non-streaming `callAi()` already genuinely supported all of them. All six providers are now genuinely wired: `chat_completions`, `chat_completions_managed`, `model_gateway`, and `structured_content` each have real, streaming-capable implementations below. Narrative generation (uses this registry) and spell-check/macros/synoptic-suggestions (use `callAi()`) are now equally provider-capable.
- **`AIAuditLog.ts`** — Logs every AI generation call.
- **`providers/StructuredMessagesProvider.ts`** — (renamed from `ClaudeProvider.ts`) Real Anthropic implementation — named for its distinctive request shape (system as a separate top-level field, SSE streaming via `content_block_delta` events) rather than the vendor.
- **`providers/ChatCompletionsProvider.ts`** — **NEW.** Real OpenAI implementation. Standard OpenAI-style SSE (`data: {"choices":[{"delta":{"content":"..."}}]}`, terminated by `data: [DONE]`) — confirmed against current OpenAI documentation before building.
- **`providers/ChatCompletionsManagedProvider.ts`** — **NEW.** Real Azure OpenAI implementation. Identical response shape to `ChatCompletionsProvider`, routed via a named deployment on a resource endpoint instead of a direct model ID, authenticated with an `api-key` header rather than a bearer token.
- **`providers/CustomProvider.ts`** — **NEW.** Real self-hosted/custom implementation. Same OpenAI-compatible shape, since this app's own design already requires a "custom" endpoint to be OpenAI-compatible (see `AiProviderSettings.tsx`'s help text).
- **`providers/openAiStyleStreaming.ts`** — **NEW.** Shared streaming parse logic for the three providers above, which genuinely share the identical protocol — extracted rather than triplicated, since duplicating the same parsing loop three times would be a real risk for silent drift/inconsistent bugs across them as each provider evolves independently.
- **`providers/StructuredContentProvider.ts`** — Real Gemini implementation. Streaming format confirmed against current Gemini API docs before building — critically, `streamGenerateContent` requires `?alt=sse` in the URL or the endpoint silently returns a single JSON array instead of a real SSE stream (an easy, documented gotcha). Also genuinely different from the other providers: no `[DONE]` terminator — the stream ends when a chunk's `finishReason` is set (typically `"STOP"`). `generateStream()` targets its own dedicated route, `/api/ai/gemini/stream`, separate from the existing non-streaming `/api/ai/gemini/generate` route, since the real upstream endpoint path itself differs. **Correction to this file's own prior claim:** that streaming route was never actually added to `vite.config.ts` — checked directly, only `/api/ai/gemini/generate` is configured. `generateStream()` therefore doesn't work as shipped; confirmed nothing in the codebase calls it. **Real fix, found while wiring voice dictation through this provider:** `generate()` previously delegated to the broken `generateStream()` — rewritten to call the proxy route that's actually configured and already proven (`testConnection()` already used it), matching this method's own documented non-streaming contract in `IAIProvider`. Adding the real `/api/ai/gemini/stream` proxy route remains open, separate work if streaming Gemini narrative generation is ever needed — `generate()` no longer depends on it.
- **`providers/ModelGatewayProvider.ts`** — **NEW.** Real Bedrock implementation, with an important, honestly-documented limitation: Bedrock's actual `InvokeModelWithResponseStream` API returns AWS's raw binary event-stream framing (`application/vnd.amazon.eventstream`) — a length-prefixed, checksummed binary protocol that every official AWS SDK example parses via a real SDK, never via a raw browser `fetch()`. Reliably re-implementing that binary framing from scratch wasn't something to do with confidence — a subtly-wrong binary parser would be worse than an honest, documented gap. This provider instead assumes the backend proxy uses a real AWS SDK server-side and re-emits the result as simple, normalized SSE (`data: {"text":"..."}` lines, `data: [DONE]` terminator) — a deliberately simple contract regardless of which underlying Bedrock model family is actually invoked. **The proxy must be built to emit this shape for this provider to work — that's a real, separate piece of backend work, not automatic from this frontend change alone.**
- **`providers/MockProvider.ts`** — Demo/offline provider, zero API cost.

## Notes

- Used directly by orchestrator/orchestratorEngine.ts — the real narrative-generation engine.
- **Now also used by voice dictation refinement** (`contexts/VoiceProvider.tsx`, via `services/aiIntegration/aiProviderService.ts`'s `callAi()`) — previously a completely separate, hardcoded-to-Gemini integration bypassing this whole abstraction. See `components/Voice/README.md` and `components/Config/AI/resolveVoiceAiModel.ts` for the voice-specific model resolution and validation-study governance layered on top.
- Distinct from services/aiIntegration/ (see that folder) — this is the low-level provider swap layer; aiIntegration/ is higher-level synoptic-suggestion logic.
- File and class renamed away from vendor names (`ClaudeProvider.ts` → `StructuredMessagesProvider.ts`) per a deliberate internal-naming decision — real vendor/model names stay in the admin UI and in comments explaining real API behavior, but internal type values, class names, and file names are protocol-shape-based instead.
- **7 real tests** in `providers/streamingProviders.test.ts` covering the shared OpenAI-style streaming helper (token emission, `[DONE]`/`finish_reason` termination, malformed-line resilience), `StructuredContentProvider`'s genuinely different `finishReason`-based termination, and `ModelGatewayProvider`'s normalized-contract parsing. Uses a real `ReadableStream`, not just a mocked `.json()` call, so the actual `reader.read()` streaming code path is genuinely exercised.
- `ModelGatewayProvider` (Bedrock) has a real, separate backend dependency that isn't automatic from this frontend change: the proxy route it calls (`/api/ai/bedrock/invoke-stream`) needs to be built server-side, using a real AWS SDK, to normalize Bedrock's raw binary event-stream response into the simple SSE contract this provider expects. Worth tracking as its own backend task.
