    # 6단계: 인터페이스 엔진 및 외부 시스템 연동

    이 장에서는 PathScribe가 다른 시스템과 메시지를 주고받는 방식을 설명합니다. 다른 시스템에는 병원의 전자 의무기록(EHR), 검사실 정보 시스템(LIS), 참조 검사실, 청구 시스템, 등록처, 보고 도구가 포함됩니다. 또한 관리자가 이러한 교환을 모니터링하고 실패한 건을 처리하는 데 사용하는 화면도 다룹니다.

    각 부분을 중심으로 프로젝트를 계획하기 전에 해당 부분의 상태를 확인하십시오. 이 단계의 상당 부분은 계약이 작성되어 있고 브라우저 측이 구현되어 있지만, 서버와 상대편 인터페이스 엔진은 아직 연결되지 않았습니다. 구현되지 않은 부분에는 해당 절에 미구현 또는 예정이라고 표시하고, 현재 존재하는 가장 가까운 기능을 함께 밝힙니다.

    이 장의 원칙. 무엇을 언제 보낼지는 PathScribe가 결정합니다. 어떻게 보낼지는 인터페이스 엔진이 결정합니다. 여기에는 HL7 텍스트, 연결, 전송 구간의 재시도, 공급업체 고유의 표현이 포함됩니다. PathScribe는 공급업체의 필드 이름이나 코드를 번역하지 않으며, 어떤 EHR에 대해서도 인증된 커넥터라고 주장하지 않습니다.

    # 6단계 설정 순서

    홈 › 구성 › 시스템 › 통합

    6단계는 대부분 선택 사항입니다. LIS, 등록처 피드, 보고 도구 없이 PathScribe를 단독으로 운영하는 검사실은 이 단계 전체를 건너뛰어도 됩니다. 사용하는 통합에 대해서만 아래 단계를 이 순서대로 수행하십시오. 각 단계에는 먼저 설정해야 하는 화면(1~5단계)이 명시되어 있으며, 같은 정보가 각 화면의 "설정 순서" 상자에도 표시됩니다.

    1. 검체 코드 매핑: 수신 주문이 처리되도록 각 송신 시설의 자체 검체 코드를 귀 검사실의 검체 사전에 매핑합니다. 시설 사전과 검체 사전이 필요합니다.
    2. 인터페이스 사전 (ForMedrixAI 직원 전용): 공급업체 고유의 필드를 기술합니다. 고객은 이 단계를 수행하지 않습니다. 번호가 빠짐없이 이어지도록 목록에 포함했습니다.
    3. LIS 수신(어시스트 모드): LIS가 케이스를 소유하고 PathScribe가 AI 초안으로 지원하는 검사실을 위한 단계입니다. AI 동작과 개요 라이브러리가 필요합니다.
    4. 보고 피드 (Power BI): 보고 도구가 PathScribe 데이터를 읽을 수 있게 합니다. 시설 사전에 수행 검사실 시설이 있어야 합니다.
    5. 마이그레이션 필드 매핑: 과거 데이터를 가져오기 전에 기존 시스템의 필드 이름을 매핑합니다.
    6. 과거 데이터 마이그레이션 작업: 기존 시스템의 파일을 가져오고 작업을 확인합니다. 5단계가 필요합니다.

    모니터링 화면(시스템 로그: 인터페이스, 인터페이스 엔진, 발신 인터페이스 DLQ, 발신 전송 내역, 발신 대기열)과 테스트 도구(발신 인터페이스 메시지 미리보기, 시뮬레이션 보낸 편지함, 모의 인터페이스 엔진, 모의 EMR)는 설정 단계가 아닙니다. 각 화면에는 Reference, not part of setup이라고 표시되어 있으며, 데이터를 표시하기 위해 무엇이 있어야 하는지가 나열되어 있습니다.

    # 이 단계에 포함되는 것과 포함되지 않는 것

    홈 › 구성 › 시스템 › 통합
    개요 항목 상태 현재 있는 것
    인터페이스 엔진 아키텍처 부분 구현 메시지 계약과 브라우저 측이 구현되어 있습니다. 엔진(BridgeLink)과 엔진에 필요한 서버 엔드포인트는 예정입니다. 인터페이스 엔진의 위치를 참조하십시오.
    송신 HL7 v2.x (ADT, ORU, ORM) 부분 구현 PathScribe는 엔진이 HL7으로 변환할 JSON 메시지를 보내며, PathScribe가 직접 HL7 텍스트로 만드는 메시지 3종은 예외입니다. 메시지 유형을 참조하십시오.
    수신 HL7 v2.x 부분 구현 처리기는 있으며 붙여 넣은 메시지로 테스트할 수 있습니다. 아직 실제 HL7 메시지를 받는 리스너는 없습니다.
    FHIR R4 엔드포인트 및 OAuth2 클라이언트 자격 증명 미구현 엔드포인트도 설정 화면도 없습니다. FHIR R4 및 OAuth2를 참조하십시오.
    EHR 연동 (Epic, Cerner, MEDITECH, AthenaHealth) 미구현 인증 여부와 관계없이 공급업체 커넥터가 없습니다. EHR 연동을 참조하십시오.
    참조 검사실 의뢰 및 결과 수신 부분 구현 의뢰 매니페스트를 전송하고 결과 페이로드를 처리합니다. 아직 결과를 받는 수신 엔드포인트는 없습니다. 참조 검사실 인터페이스를 참조하십시오.
    인터페이스 모니터링, 오류 대기열 및 재처리 구현됨 (브라우저 측) 화면과 해당 권한이 작동합니다. 엔진 하트비트와 엔진 측 재시도는 예정입니다. 모니터링을 참조하십시오.

    # "PathScribe 인터페이스 엔진"이라는 용어

    홈 › 구성 › 시스템 › 통합

    이 가이드의 개요에서는 인터페이스 계층을 PathScribe 인터페이스 엔진(PIE)이라고 부릅니다. 이 이름은 제품, 제품의 화면, 설계 문서 어디에도 나타나지 않으며, 이 가이드는 제품 이름을 새로 만들지 않습니다. 제품에는 개요가 설명하는 일을 함께 수행하는 두 가지가 있습니다.

    • PathScribe 측. 애플리케이션의 서비스가 무엇을 언제 보낼지 결정하고, JSON 메시지를 만들고, 대기열에 넣고, 결과를 기록하며, 관리자가 메시지를 다시 보내거나 보류하거나 해제할 수 있게 합니다. 이 장에서 클릭할 수 있는 모든 것은 이 측에 있습니다.
    • 인터페이스 엔진. 설계에서는 Mirth Connect의 오픈 소스 포크인 BridgeLink를 엔진으로 사용합니다. 엔진은 PathScribe의 JSON을 HL7(또는 다른 형식)으로 변환하고, 자체 메시지 저장소를 보유하며, 수신 시스템으로 전송하고, 회신을 받습니다. BridgeLink는 설계 문서(INTERFACE_ENGINE_EDGE.md)에서 쓰는 작업 명칭입니다. 채널 템플릿은 예정이며 구현되지 않았습니다.

    # 엔진이 실행되는 위치

    홈 › 구성 › 시스템 › 통합

    엔진은 하나의 컨테이너 이미지이며 병원별로 선택하여 두 곳에서 사용합니다(결정 D6). ForMedrixAI가 테넌트의 지역에서 엔진을 호스팅하거나, 병원 내부의 가상 머신에 엔진을 설치할 수 있습니다. 인터페이스 엔진 화면에는 각 엔진이 둘 중 어느 쪽인지(호스팅 또는 현장)가 표시됩니다. 이미지, 채널 템플릿, 상태 확인 엔드포인트는 서버 팀과 함께 예정되어 있습니다.

    HL7 메시지는 SQL Server 메시지 버스로 이동하지 않습니다(결정 D1). API 서버는 interface.dispatch 유형의 작업으로 메시지를 엔진에 넘기며, 엔진은 HL7을 자체 메시지 저장소에 보관합니다.

    # 현재 실행되는 것과 예정된 것

    홈 › 구성 › 시스템 › 통합
    구성 요소 상태 사용자에게 의미하는 바
    송신 메시지, JSON 봉투 구현됨 (브라우저 측) 브라우저는 {queueEntryId, transactionType, dispatchedAt, payload}를 빌드 설정 VITE_INTERFACE_RECEIVER_ENDPOINT의 주소로 전송합니다. 운영 빌드에서는 주소가 https여야 하며, 주소가 없거나 일반 HTTP이면 아무것도 전송하기 전에 거부됩니다. 대기 시간은 15초입니다.
    전송된 것으로 간주하는 기준 구현됨 (브라우저 측) 2xx 응답이면 메시지가 전송된 것으로 표시됩니다. 아직 HL7 확인 응답(ACK)은 없습니다. 시간 초과, 엔진에 연결할 수 없음, 거부는 화면에서 서로 다른 세 가지 오류입니다.
    데모 빌드 데모 엔진 주소가 설정되지 않으면 모의 엔진이 모든 메시지를 받아 목록에 보관합니다. 모의 인터페이스 엔진을 참조하십시오.
    기기에서 오는 수신 이벤트 구현됨 (브라우저 측) 카세트 엔진용 웹훅이 4개 있습니다. 블록 예외, 카세트 전송 결과, 재료 위치, 각인기 상태입니다. X-API-Key 헤더의 공유 비밀 값을 사용하며, HMAC 서명은 선택 사항입니다.
    수신 HL7 메시지 미구현 ADT 및 환자 관리 처리기는 있으며 테스트되었지만, 실제 HL7 메시지를 받아 이를 호출하는 구성 요소는 없습니다.
    엔진용 서버 엔드포인트 (POST /api/interface/inbound, POST /api/interface/outbound-acks, POST /api/interface/heartbeat, GET /api/interface/engines) 예정 계약(2e 단계)으로 작성되어 있습니다. 인계, 확인 응답으로 확정되는 결과, 재시도 구간, 데드 레터, 엔진 상태를 추가합니다.
    테넌트별 엔진 자격 증명 예정 테넌트 엔진마다 OAuth2 클라이언트 자격 증명 또는 상호 TLS를 사용합니다. FHIR R4 및 OAuth2를 참조하십시오.

    예정된 재시도 구간. 계약에 따르면 수신 메시지는 10초, 30초, 1분, 5분, 15분 동안 대기하며 24시간 후에 데드 레터가 됩니다. 송신 메시지는 1분, 5분, 15분, 60분에 다시 보내고, 이후 24시간 동안 매시간 다시 보냅니다. 등록처 제출 건은 72시간 동안 보관합니다. AA 확인 응답이 전송됩니다. CA는 전송되거나 애플리케이션 확인 응답을 기다립니다. AR과 CE는 구간 내에서 재시도하며, AE와 CR은 즉시 실패합니다. 데드 레터가 된 결과는 같은 케이스의 이후 메시지를 보류합니다. 이 중 현재 실행되는 것은 없습니다. 현재는 전송에 실패하면 관리자가 다시 보낼 때까지 대기합니다.

    # 저장되지만 사용되지 않는 시설 인터페이스 설정

    홈 › 구성 › 시스템 › 통합

    시설 편집기(1단계, 시설 사전)에는 LIS 연동 탭이 있습니다. 이 탭에는 엔진 주소, HL7 버전, 인증 유형(없음, 기본, OAuth2 또는 API 키), 자격 증명이 프로비저닝되었는지 나타내는 플래그, LIS가 케이스 상태를 소유하는지 여부, PathScribe가 최종 확정 후 작업을 허용하는지 여부, 송신 시설과 수신 시설의 라우팅 식별자, 송신 채널 재정의가 저장됩니다. 이 설정은 시설과 함께 저장됩니다. 현재 이 설정을 읽는 전송 경로는 없으며, 메시지는 위에서 설명한 배포 수준의 단일 주소로 전송됩니다. 자격 증명은 저장되지 않고 예/아니요 플래그만 저장됩니다.

    구현된 것과 구현되지 않은 것. 구현됨: 설정, 상태 매핑, 테스트 상자, 재시도가 있는 수신 대기열, 실행 로그, AI 초안 작성 규칙. 데모에서 시뮬레이션됨: 일정(앱이 열려 있고 폴링이 켜져 있는 동안 저장된 간격으로 폴링하며, 화면에는 마지막 실행과 다음 실행이 있는 시뮬레이션 일정 안내가 표시됩니다)과 지금 조회가 요청하는 LIS. 구현되지 않음: HL7 또는 웹훅 메시지를 받는 실제 리스너와 조회할 LIS의 주소를 입력하는 필드. 화면에는 그러한 필드가 없습니다.

    # 참조 검사실 인터페이스

    홈 › 구성 › 시스템 › 통합

    상태: 부분 구현

    참조 검사실은 분자 검사나 외부 의뢰 면역조직화학 검사처럼 외부 위탁 검사를 위해 검체를 보내는 시설입니다. PathScribe는 매니페스트로 하는 의뢰 발송과 결과 메시지로 하는 결과 수신을 지원합니다. 송신 측은 구현되어 있으며, 수신 측에는 처리기는 있지만 엔드포인트는 없습니다.

    "참조 검사실 인터페이스"라는 화면은 없습니다. 설정은 이미 있는 여러 화면에 나뉘어 있습니다.

    1. 검사실을 시설로 만듭니다. 시설 사전에서 검사실을 추가하고 참조 검사실(발신 의뢰 대상) 역할을 지정합니다. 이 역할이 있어야 의뢰 배치의 대상으로 선택할 수 있습니다. 해당 역할이 있는 활성 시설만 표시됩니다.
    2. 수행하는 검사와 연결합니다. 진단 카탈로그에서 분자 검사에는 해당 검사를 수행하도록 승인된 참조 검사실과 그중 기본 검사실이 나열됩니다. 기본 검사실은 승인된 검사실 중 하나여야 합니다. 이 연결은 분자 범주에만 유지되며, 해당 검사의 추가 주문은 기본 검사실을 채우고 승인된 검사실만 표시합니다.
    3. 발송합니다. 의뢰 배치는 배치 관리에서 처리 노드 외부 의뢰와 대상 시설을 지정하여 만듭니다. 배치가 대조를 완료하면 PathScribe는 REFERRAL_MANIFEST 메시지를 대기열에 넣고 추적 기록을 자동으로 만듭니다. 여기서 발생한 실패가 배치 자체의 완료를 막지는 않습니다. 매니페스트에는 배치 ID, 마스터 바코드, 대상 시설, 요청한 검사, 우선순위(STAT 또는 Routine), 항목(표시 ID, 재료 유형, 케이스 접수번호, 검체 라벨), 그리고 외부 의뢰 분자 검사 주문이 들어 있습니다. 무엇을 언제 보낼지는 PathScribe가 결정하고 전송 방식은 엔진이 결정합니다.
    4. 발송을 확인합니다. 메시지는 발신 대기열에서는 피드 의뢰에, 발신 인터페이스 DLQ에서는 대기열 의뢰 송장에 나타나며, 실패한 메시지는 여기서 다시 보냅니다.
    5. 결과를 수신합니다. 결과 메시지(ReferralResultEventPayload)에는 배치 ID와 discrete 결과(텍스트) 또는 pdf_attachment(PDF 링크) 중 하나가 들어 있으며 둘 다 들어 있는 경우는 없고, 선택적으로 외부 의뢰 분자 검사 주문별 결과도 들어 있습니다. 처리기는 형식을 확인하고, 배치를 찾고, 결과를 기록하고, 배치를 result_received로 표시한 다음 코드화된 결과를 분자 검사 주문에 적용합니다. 배치의 상태는 발송됨, 운송 중, 전달됨, 결과 수신됨의 순서로 앞으로만 이동합니다. 사람이 운송 중과 전달됨을 직접 설정할 수 있으며, 결과 수신됨은 결과가 도착할 때만 설정됩니다.

    구현되지 않은 것. 결과 메시지를 받는 엔드포인트가 없으므로 참조 검사실에서 결과가 저절로 도착하지 않습니다. 처리기는 처리한 메시지 ID를 메모리에만 기억하므로 재시작하면 잊어버립니다. 처리기는 적용됨, 이미 적용됨, 추적 정보를 찾을 수 없음, 잘못된 페이로드의 네 가지 응답 중 하나를 반환합니다. 모의 인터페이스 엔진에는 의뢰 결과용 테스트 샘플이 없습니다. 참조 검사실 고유의 표현(검사 이름과 결과 코드)은 PathScribe가 번역하지 않으며 엔진이 담당합니다.

    # 재처리 규칙 한눈에 보기

    홈 › 품질 및 준수

    송신 메시지의 전송 실패 발신 인터페이스 DLQ 및 발신 대기열의 실패 전송 재시도 또는 지금 전송으로 엔진에 다시 보냅니다. interface:outbound:resend
    메시지를 아직 보내지 않아야 함 발신 대기열, 대기 중 또는 실패 사유를 입력하여 보류한 다음 해제합니다. 보류된 메시지는 다른 어떤 작업으로도 전송되지 않습니다. 재시도하면 "발신 대기열에서 보류됨: 먼저 그곳에서 해제하세요."라고 표시됩니다. interface:outbound:hold, interface:outbound:release
    자동 재시도 이후에도 메시지가 실패함 발신 대기열, 재시도 소진 재시도, 또는 청구 항목의 경우 청구 철회. interface:outbound:resend, interface:outbound:retract
    등록처가 제출을 거부함 발신 대기열, 거부됨 사유를 입력하여 재시도(재제출)하거나, 사유를 입력하여 보고 대상 아님으로 표시합니다. interface:outbound:resend, interface:outbound:mark-not-reportable
    수가를 일찍 내보내거나 취소해야 함 발신 대기열, 청구 항목 지금 해제 또는 청구 철회. interface:outbound:override-release, interface:outbound:retract
    보고서 인쇄, 팩스 또는 파일 전달이 재시도 후에도 실패함 발신 인터페이스 DLQ 맨 위의 전달 예외 해당 대기열(인쇄 대기열 또는 보고서 전달)에서 다시 보냅니다. 성공하면 목록에서 사라집니다. 보고서 전달에는 interface:outbound:resend
    대기열에 있던 수가가 실패함 시스템 로그의 발신 DLQ 하위 탭, 재무 (7단계) 시스템 로그: 재무를 참조하십시오. 해당 화면 참조
