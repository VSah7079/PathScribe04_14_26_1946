# Report rendering service (server PDF): Microsoft.Playwright / headless Chromium

**Decision (Pete, Oct 5, 2026, Batch 463):** the production report PDF is rendered by the ASP.NET Core API server as **HTML → PDF through headless Chromium, driven by `Microsoft.Playwright`** ("Option A" in `ORGAN_MAPPING_API.md` §5). It replaces the interim Python renderer (`functions/main.py`, ReportLab) for production. Organ maps (Mohs stage maps and the others) go into the HTML as SVG and stay vector in the PDF; nothing is rasterised.

This document is the contract for the dev team. Pete's controls are below, with the adjustments made on review (marked **Adjusted**) where the first wording would have weakened isolation or reliability.

## 1. Instance pooling and lifecycle (`PlaywrightHostPool`)

Launching a Chromium per request causes CPU/RAM spikes. The singleton service keeps browsers warm.

- **Pool the browsers, not the contexts.** **Adjusted:** keep a small pool of warm **`IBrowser` processes** (start with 2, configurable up to 4 by measured load), and create a **fresh `IBrowserContext` and `IPage` for every report**, disposed when it finishes. A context is the isolation boundary (cache, storage, cookies, service workers) and costs milliseconds to create; reusing contexts across reports would let one patient's report share browser state with the next. The browser processes are what is expensive, so those are what the pool holds.
- **Per-report limits.** Close the page and its context on completion, error or timeout (`try/finally`, `await using`). Hard timeout per report: **5 s by default, configurable**; a long multi-part report or one with several maps must be measured against it. **Adjusted:** a timeout or crash never produces a partial PDF: the render fails, is retried once on a different (or freshly started) browser, and then reports an error to the caller; the sign-out keeps its existing retry path. Concurrency per browser is capped (a semaphore), so a burst queues instead of exhausting memory.
- **Recycling.** Dispose and restart a browser after **N renders (500 by default)**, when its memory passes a configured ceiling, or after it crashed or timed out. Recycle one browser at a time so the pool never empties; drain its in-flight pages first.
- **Health.** The service exposes readiness (a browser is up and a trivial page renders) and metrics: renders, failures, timeouts, recycles, render time, pool waits.
- Playwright talks to Chromium over pipes, not network ports; "port exhaustion" is not the failure mode, memory and process count are.

## 2. Clinical data and network isolation

The page is built from patient data. Nothing it contains may reach the network, and nothing in it may run.

- **No network from the page**, enforced twice:
  - `BrowserNewContextOptions { Offline = true, JavaScriptEnabled = false }` as Pete specified.
  - **Adjusted (added):** `Offline` emulates a dropped connection; it is not a filter. Also route every request to abort (`context.RouteAsync("**/*", r => r.AbortAsync())`) and load the report with `page.SetContentAsync(html)`, so the only content is the HTML string itself. Log any aborted request: a template that tries to fetch something is a defect.
  - **Adjusted (added):** at the container level, the rendering service has **no egress** (network policy / firewall). The API server talks to it; it talks to nobody.
- **Inline assets only.** CSS in `<style>`, logos as `data:` URIs, fonts installed in the image (section 3) or embedded as `data:` `@font-face`. **Adjusted:** no `file://` URLs from the page: with JavaScript off and escaping on they shouldn't be reachable, but a page that can name local files is one injection away from printing them.
- **Escaping.** Templates are compiled with an HTML-encoding engine: Razor (encodes by default) or Fluid configured with `HtmlEncoder.Default` for every output. Patient names, specimen descriptions, diagnoses, comments and every synoptic answer are encoded; raw-HTML output helpers are banned except for the server's own generated SVG. Never place data inside `<style>`, `<script>` or unquoted attributes.
- **Maps are drawn by the server.** The organ-map SVG in the page is generated by the server from the signed synoptic answers (the `organMapping/` resolver and drawing, ported); a browser-supplied SVG is not embedded. Its fingerprint must match the one recorded at sign-out.
- **JavaScript off is compatible with the PDF features used:** `page.PdfAsync` with `DisplayHeaderFooter` and the `pageNumber` / `totalPages` classes in header/footer templates works without page scripts.
- **PHI in logs:** log case and request ids, never the HTML, names or answers.

## 3. Container runtime and Linux dependencies

- **Base image and browser.** Use the version of Chromium that matches the pinned `Microsoft.Playwright` package, installed **into the image at build time** (`playwright.ps1 install --with-deps chromium`, or Microsoft's Playwright .NET image as the base). Never download browsers at runtime: private-cloud and air-gapped deployments have no internet.
- **Fonts.** `fonts-liberation` (Latin metric-compatible with Arial/Helvetica, which the maps name), **`fonts-noto-cjk`** (Korean; large, about 100 MB+, which is accepted), plus `fonts-dejavu-core` for symbols. Pretendard may be added to match the current Korean PDFs. A Korean report and a map with Korean labels are part of the image's acceptance test.
- **Non-root.** Chromium runs as a dedicated non-root user (`USER appuser`).
- **Sandbox. Adjusted:** do **not** grant `CAP_SYS_ADMIN`: it is close to root inside the container and is a larger risk than the one it mitigates. Keep Chromium's own sandbox working with unprivileged user namespaces and the Chromium seccomp profile (Playwright's Docker guidance provides one). Only if a hosting platform cannot allow that may `--no-sandbox` be used, and then only with the container itself locked down: non-root, all capabilities dropped, read-only root filesystem, no egress, no other workloads in it. The choice is recorded per deployment.
- **Shared memory.** Docker's default `/dev/shm` (64 MB) crashes Chromium on large pages: give the container a larger `/dev/shm` (or `--ipc=host` where acceptable), or launch with `--disable-dev-shm-usage`.
- **Patching.** Chromium security releases are frequent. The image is rebuilt and revalidated on that cadence under change control; the Playwright/Chromium version is part of each report version's audit metadata (renderer name and version).

## 4. Output requirements carried over

- The PDF hash stored on the report version is of the PDF actually produced (each PDF is unique: creation date).
- A map that is part of the report and cannot be drawn prints the notice with its content as text (`ORGAN_MAPPING_API.md` §5; `surgicalReportPdf.figureNotDrawn`), recorded on the report version; the request still succeeds.
- **Open checks before go-live:** PDF/A (Chromium doesn't produce it; add a conversion step if a customer or regulator requires archival PDF/A); tagged (accessible) PDF output; header/footer templates against today's continuation-page headers (since Batch 539 the cytology template's, `functions/cytology_report.py`); layout parity with the HTML preview (`pages/ReportPreview/ReportPreviewRenderer.tsx`).

## Summary for sign-off

| Control | As specified | As adopted |
|---|---|---|
| Pool | 2–4 reused `IBrowserContext` | 2–4 warm `IBrowser` processes; a new context + page per report |
| Timeout | 5 s hard | 5 s default, configurable; fail and retry once, never a partial PDF |
| Recycling | After N (500) or memory | Same, one browser at a time, after draining |
| Network | `Offline = true`, JS off | Plus abort-all routing, `SetContentAsync`, container with no egress |
| Assets | Inline or local files | Inline / installed fonts; no `file://` from the page |
| Escaping | Razor or Fluid, strict | Same; server-drawn SVG only raw content |
| Fonts | liberation, noto-cjk | Same, plus dejavu; Korean acceptance test |
| Sandbox | `--no-sandbox` if isolated, or `CAP_SYS_ADMIN` | Native sandbox via user namespaces + seccomp; never `CAP_SYS_ADMIN`; `--no-sandbox` only in a locked-down container, recorded |
| Memory | — | Larger `/dev/shm` or `--disable-dev-shm-usage` |
| Patching | — | Rebuild on Chromium security releases; renderer version in the audit |

## 5. Content rules to carry over from the interim renderer (Batch 498)

The interim renderer (`functions/main.py`) now prints these; the production service must too:

- **Release-buffer watermark** (`watermarkText`, only while a case is pending release): on every page, behind the text.
- **Revision status** (`revision`): a banner in the header area — amended / corrected / with addendum, original sign-out date and latest revision date (dates written in the report's locale by the app) — and the revision flag in every page's footer.
- **Footer document reference**: Code 128 of the accession (scannable back to the case) plus the record version, on every page.
- **Pre-analytic override disclaimer** (`preAnalyticDisclaimerText`): before the report body.
- Wording from the request's `labels` (`surgicalReportPdf.*`), never hard-coded.

## 6. Preview and release from one payload (Batch 538)

Pete, Oct 12, 2026: the server makes every PDF that leaves PathScribe, and the browser only shows previews, "as long as the preview matches exactly what gets sent out".

- **One payload builder.** The report page builds one payload for both the released PDF and the preview or print (`buildReportRenderPayload(outputFormat, purpose)` in `SynopticReportPage.tsx`). The purpose changes only the watermark (`services/reports/resolveReportWatermark.ts`): an unsigned print says "PRELIMINARY — SUBJECT TO CHANGE". Before Batch 538, print built a separate payload.
- **Server endpoints.** The API server offers the same split:
  - `POST /api/cases/{caseId}/report-preview` renders without storing;
  - the release renders once and stores the document (`REPORT_DOCUMENT_STORE_API.md`).
- **After release,** "View as sent" opens the stored document, never a fresh render.

## 7. Cytology (Batch 539)

The report renderer has a cytology template (`functions/cytology_report.py`, reached through `render_report` with `"template": "cytology"`). The browser composes every line of the report in its language (`src/services/cytology/cytologyRenderPayload.ts`); the template lays it out:
- A4, 15 mm margins (never below the 0.5 inch printing minimum);
- Liberation Sans embedded (Pretendard for Korean), chosen per document, so a case report can mix languages;
- the accession barcode (Code 128) on each report's first page, and a continuation line with "Page X of Y" on the others;
- an unsigned preview's watermark;
- the same bytes for the same request (creation date is the signing time; fixed document ID).

The preview and the release send the same lines; only the preview's watermark differs. Each PDF carries `pathscribe-template:cytology` in its Keywords: the browser refuses a PDF without it, so a renderer deployed before Batch 539 holds the release instead of sending a blank page. The production renderer (Playwright, §4) must keep the same contract: the request in `cytology_report.py`'s header, and the marker.
