# 3단계: 워크플로 엔진 및 운영 구성 (세 번째로 설정) {#ch4}

3단계는 1단계와 2단계의 사용자, 시설, 장비, 사전이 갖추어진 뒤에 업무가 어떻게 흘러가는지를 정하는 구성 영역입니다. 케이스를 어디로 라우팅할지, 작업대가 어떤 명령과 매크로를 제공할지, 서명 전후에 케이스를 어떻게 보류하여 검토할지, 처리 시간과 품질을 어떻게 측정할지를 다룹니다. 세 번째로 설정하십시오. 이 단계의 화면 대부분은 1단계 또는 2단계의 사전(시설, 세부 전문 분야, 검체 유형)을 읽어 오며, 해당 사전이 채워질 때까지 선택 목록이 비어 있습니다.

시작하기 전에 읽어 두십시오. 제품의 화면 제목에서 짐작되는 내용과 다른 점이 네 가지 있습니다.

- **"오더 입력 워크플로 템플릿"이나 "접수 워크플로 템플릿"은 없습니다.** 접수 동작은 각 설정이 있는 곳에 문서화된 여러 설정에 나뉘어 있습니다. [접수 설정이 있는 곳](#ch4-accession-settings)에 목록이 있습니다. **미구현.**
- **일부 화면은 값을 설정에 사용한 컴퓨터의 브라우저에 보관합니다**(케이스 라우팅, 라우팅 규칙, 작업 레지스트리, 잉킹 검증 모드, 후속 조치 추적, 생검-절제 상관 관계, 기여도 설정, 그리고 음성 탭의 배포 스위치). 화면의 상태에 이 점이 표시됩니다. 이러한 설정은 API 서버 버전이 나올 때까지 다른 워크스테이션에서 보이지 않습니다.
- **디지털 병리는 대부분 공급업체 사전입니다.** PathScribe는 공급업체와 뷰어 실행 주소를 나열할 뿐이며, 스캐너 드라이버가 없고 슬라이드 영상을 직접 표시하지도 않습니다. [디지털 병리](#ch4-digital-pathology)를 참조하십시오.
- **거의 모든 서명 및 품질 설정에는 조직 기본값과 검사실별 재정의가 있습니다.** 재정의는 시설 구성 편집 창([시설 사전](#screen-facility-dictionary))이나 화면 안에서 설정합니다.

3단계는 다음 순서로 설정하십시오. 각 설정 화면에는 같은 정보를 담은 설정 순서 상자가 있으며, 빌더는 어떤 화면도 자신보다 뒤에 오는 화면을 필요로 하지 않는지 확인합니다. 참조로 표시된 화면은 일상 업무용 페이지이며 설정이 아닙니다.

## 오더 입력 및 접수: 라우팅과 작업 묶음 {#ch4-order-entry}
Breadcrumb: 홈 > 구성

이 부분은 케이스가 생성된 뒤 어디로 가는지, 그리고 워크스테이션이 어떤 명령을 제공하는지를 정하는 설정을 다룹니다. 먼저 [접수 설정이 있는 곳](#ch4-accession-settings)을 읽으십시오. PathScribe에는 단일 "오더 입력 워크플로 템플릿" 화면이 없으며, 그 절에서 대신 무엇이 있는지 설명합니다.

### 접수 설정이 있는 곳 {#ch4-accession-settings}
Breadcrumb: 홈 > 구성 > 시스템

**상태:** 부분 구현

현재 PathScribe에는 구성할 수 있는 "오더 입력 워크플로 템플릿" 또는 "접수 워크플로 템플릿" 화면이 없습니다. **미구현.** 접수 화면(홈 > 접수)은 아래의 사전과 규칙에서 동작을 읽어 오며, 각각은 자체 화면에서 설정합니다. 접수 화면 자체에는 별도의 설정 페이지가 없습니다. 이 목록은 접수 화면이 호출하는 서비스를 기준으로 작성되었습니다.

| 접수 시 달라지는 항목 | 설정하는 곳 | 장 |
|---|---|---|
| 접수번호 형식 | [케이스 마스크 구성](#screen-case_mask_config) | 1단계 |
| 케이스를 접수하기 전에 채워야 하는 필드(페이지 id `accession` 및 `clinicalHistory`) | [필수 입력 항목](#screen-field_requirements) | 1단계 |
| 부서 목록과 부서가 처음 사용하는 육안 검사 템플릿 | [부서](#screen-departments) | 2단계 |
| 검체 선택 목록과 용기 선택 목록 | [검체 사전](#screen-specimens) 및 [용기 유형](#screen-container_types) | 2단계 |

인터페이스 엔진에서 들어오는 오더는 6단계의 오더 유형 및 인바운드 규칙에서 설정하는 검체 코드 크로스워크로 매칭됩니다. 수신 오더, 크로스워크, 초안, 접수 발신 대기열에 대한 서버 호출은 `docs/architecture/ACCESSIONING_API.md`에 기재되어 있습니다.

**알려진 제한 사항.** 예정: 워크플로별로 이러한 설정을 묶는 템플릿. 일정은 정해지지 않았습니다. 그때까지는 각 설정을 해당 화면에서 변경합니다.

### 라우팅 규칙 {#screen-routing_rules}
Breadcrumb: 홈 > 구성 > 시스템 > 통합 > 라우팅 규칙

**상태:** 데모

**1. 탐색:** 구성 탭 **시스템** > 그룹 **통합**
**2. 관리 항목:** 라우팅 규칙

**3. 업무 목적 및 범위.** 라우팅 규칙은 검체 설명에 있는 단어를 매칭하여 케이스를 세부 전문 분야 풀로 보냅니다. 이 화면은 키워드 규칙을 위한 간단한 편집기이며, 규칙 하나는 풀, 키워드 목록, 우선순위, 메모로 이루어집니다. 규칙은 우선순위 순서로 확인하고 처음 일치하는 규칙이 적용됩니다. PathScribe에는 내장 규칙 8개가 포함되어 있습니다(대장, 상부 위장관, 간담췌, 유방, 비뇨생식기, 부인과, 피부병리, 혈액병리; 우선순위 10에서 60). 내장 규칙은 편집하거나 끌 수 있지만 삭제할 수 없습니다. 같은 규칙이 [케이스 라우팅](#screen-case_routing)에도 더 많은 옵션(검체 유형 매칭, 수행 검사실, 검사실별 대체 풀)과 함께 표시되며, 두 화면은 하나의 저장된 목록을 읽고 씁니다.

**4. 선행 조건 및 종속 관계.** 규칙은 풀을 가리키며, 풀은 **풀 / 작업 그룹**이 켜진 세부 전문 분야입니다. 세부 전문 분야를 건너뛰면 **풀로 라우팅** 목록이 비어 있고 경고가 표시되며 규칙을 저장할 수 없습니다.

Requires: [세부 전문 분야](#screen-subspecialties)
Unlocks: [케이스 라우팅](#screen-case_routing)

**5. 화면.**

**6. 필드 참조.**

|---|---|---|---|---|
| 라우팅 테스트(검체 설명) | 텍스트 | 선택 | 설명을 입력하고 **테스트**를 선택합니다. 화면에는 처음 일치하는 활성 규칙의 풀과 해당 규칙의 메모 및 우선순위가 표시되며, 일치하는 규칙이 없으면 케이스가 대체 풀로 가게 된다는 경고가 표시됩니다. 키워드 규칙만 테스트하며 항상 전역 규칙 세트로 테스트합니다(수행 검사실은 적용되지 않음). | 공백 |
| 키워드 또는 메모 검색 | 텍스트 | 선택 | 키워드 또는 메모 텍스트로 목록을 필터링합니다. | 공백 |
| 라우팅 규칙 필터 | 선택: 전체, 활성, 비활성, 사용자 지정만 | 선택 | 목록을 필터링합니다. **사용자 지정만**은 내장 규칙을 숨깁니다. | 전체 |
| 우선 | 정수 | 해당 없음 | 목록에 표시되는 우선순위입니다. 낮을수록 먼저 확인합니다. | 해당 없음 |

| 키워드 | 칩 | 해당 없음 | 처음 8개의 키워드가 표시되고 이어서 "+N개 더"가 표시됩니다. | 해당 없음 |
| 메모 | 텍스트 | 해당 없음 | 규칙의 메모입니다. | 해당 없음 |
| 상태(목록 스위치) | 활성 / 비활성 스위치 | 선택 | 규칙을 즉시 켜거나 끕니다. 변경 사항은 자동으로 저장됩니다. | 해당 없음 |
| 편집, 복제, 삭제 | 행 버튼 | 해당 없음 | **복제**는 규칙의 복사본이 미리 채워진 **라우팅 규칙 추가** 창을 엽니다. **삭제**(사용자 지정 규칙만)는 확인을 요청한 뒤 규칙을 제거합니다. 내장 규칙에는 **삭제**가 표시되지 않습니다. | 해당 없음 |

| 키워드 | **추가**나 Enter로 입력한 단어이며 칩으로 표시됨 | 필수(최소 1개) | 검체 설명에 키워드가 하나라도 포함되면 규칙이 일치합니다. 매칭은 대소문자를 구분하지 않으며 부분 일치이고 문장 부호는 무시합니다. 이미 목록에 있는 키워드는 거부됩니다. 키워드는 소문자로 저장됩니다. | 없음 |

| 메모(선택) | 텍스트 | 선택 | 관리자를 위한 자유 텍스트입니다. 목록에서 검색할 수 있습니다. | 공백 |
| 상태 | 활성 / 비활성 스위치 | 선택 | 비활성 규칙은 라우팅할 때 건너뜁니다. | 활성 |

**7. 권한.** 화면 열기: `screen:configuration:open`. 추가, 편집, 복제, 삭제, 켜기 또는 끄기: `config:case-routing:manage`(고위험이므로 모든 확인이 감사 로그에 기록됩니다). Admin과 Lab Director가 기본으로 보유하며, Superadmin은 전체 카탈로그를 보유합니다 (단, `config:ai-prompt:approve`는 직무 분리를 위해 제외됩니다).
**알려진 제한 사항.** 규칙은 브라우저의 데모 저장소에 보관되며, 라우팅 규칙에 대한 서버 계약은 아직 없습니다(`docs/architecture/ROUTING_API.md`의 `routing-rules` 서버 호출은 다른 기능인 시설, 의사, 프로토콜 매핑을 위한 것입니다). 이 화면에서는 수행 검사실을 설정하거나 검체 유형으로 매칭할 수 없으며, 이러한 작업에는 [케이스 라우팅](#screen-case_routing)을 사용하십시오. 중복된 우선순위를 거부하는 이 화면의 우선순위 확인은 케이스 라우팅에는 적용되지 않습니다.

### 케이스 라우팅 {#screen-case_routing}
Breadcrumb: 홈 > 구성 > 시스템 > 통합 > 케이스 라우팅

**상태:** 데모

**1. 탐색:** 구성 탭 **시스템** > 그룹 **통합**
**2. 관리 항목:** 케이스 라우팅

**3. 업무 목적 및 범위.** 케이스 라우팅은 병리의가 배정되지 않은 케이스가 세부 전문 분야 풀에 도달하는 방식을 정합니다. 이 화면에는 마스터 스위치, 대체 풀(전역 풀 하나와 수행 검사실별 선택적 재정의), 검체 유형 및 수행 검사실 범위를 지정할 수 있는 라우팅 규칙, 테스트 상자, 미배정 케이스를 지금 모두 라우팅하는 버튼이 있습니다. 화면의 "라우팅 작동 방식" 다이어그램은 순서를 보여 줍니다. 케이스가 도착하면 PathScribe는 직접 배정을 확인하고(이미 병리의가 있는 케이스는 그대로 둠), 이어서 해당 검사실의 자체 규칙, 전역 규칙, 해당 검사실의 대체 풀, 전역 대체 풀 순으로 확인하며, 해당 풀이 없으면 케이스에 수동 배정 플래그를 지정합니다. 세부 전문 분야에서 Default / Catch-All로 태그된 풀은 여기에서 설정한 대체 풀보다 우선합니다.

**라우팅이 실행되는 시점.** 라우팅은 케이스의 육안 검사가 완료될 때(STAT 케이스는 STAT 경로를 사용) 실행되며, 실제 진단 업무가 처음 시작될 때 한 번만 실행됩니다. 접수 시에는 실행되지 않습니다. 검체가 없는 케이스는 라우팅되지 않습니다.

**4. 선행 조건 및 종속 관계.** 풀은 [세부 전문 분야](#screen-subspecialties)(풀 / 작업 그룹이 켜진 항목)에서, 검체 유형은 [검체 사전](#screen-specimens)에서, 수행 검사실은 [시설 사전](#screen-facility-dictionary)(수행 검사실 역할을 가진 시설)에서 가져옵니다. 풀을 건너뛰면 화면에 "활성 풀을 찾을 수 없습니다"가 표시되고 대체 풀을 선택할 수 없으며, 시설을 건너뛰면 검사실별 표와 검사실 선택 목록이 비어 있습니다.

Setup step: Tier 3, step 2
Requires: [라우팅 규칙](#screen-routing_rules), [세부 전문 분야](#screen-subspecialties), [검체 사전](#screen-specimens), [시설 사전](#screen-facility-dictionary)
Unlocks: 없음.

**5. 화면.**

### 작업 그룹 {#screen-action_groups}
Breadcrumb: 홈 > 구성 > 시스템 > 실험실 자재 및 워크플로 > 작업 그룹

**상태:** 구현됨

**1. 탐색:** 구성 탭 **시스템** > 그룹 **실험실 자재 및 워크플로**
**2. 관리 항목:** 작업 그룹

**3. 업무 목적 및 범위.** 작업 그룹은 작업 레지스트리의 명령을 이름 붙여 묶은 것입니다(예: "Log Slide / Block"). 워크스테이션 그룹은 기본으로 허용하는 작업과 추가할 수 있는 작업에 대해 작업 그룹을 참조합니다. 하나의 작업이 둘 이상의 그룹에 속할 수 있습니다.

**4. 선행 조건 및 종속 관계.** 그룹은 [작업 레지스트리](#screen-tab-actions) 탭에 나열된 명령에서 선택합니다. 작업을 하나도 선택하지 않으면 그룹을 저장할 수 없습니다.

**2. 관리 항목:** 잉킹 검증 모드

**3. 업무 목적 및 범위.** 구조화된 잉킹 확인은 누군가 **육안검사 완료**를 선택할 때와 서명 시 다시 한 번 케이스의 모든 절제연을 살펴봅니다. 세 종류의 문제를 찾아냅니다. 검사됨으로 표시되지 않은 절제연(심각도 2), 잉크가 기록되지 않은 절제연(심각도 2), 활성 잉크 색상 사전에 없는 잉크 색상 코드(심각도 3)입니다. 이 화면에서는 한 시설에 대해 **경고만 표시**와 **엄격 적용** 중 하나를 선택합니다.

**현재 코드의 동작(소스에서 확인함).** 화면 텍스트에는 엄격 적용이 심각도 2 문제에서 **육안검사 완료**를 완전히 차단한다고 되어 있습니다. 육안검사 완료를 막는 게이트는 어느 모드에서도 그렇게 동작하지 않습니다.
- 심각도 3(매핑되지 않은 잉크 색상)은 항상 육안검사 완료를 차단합니다. 서명 시에는 차단하거나, `case:inking-gate:override` 권한을 가진 사람에게 재정의를 요청합니다.
- 육안검사 완료 시 심각도 2는 **권고 메모와 함께 진행** 확인을 표시한 다음 육안 검사를 완료하도록 허용하며, 이는 두 모드 모두 같습니다.
- 현재 눈에 띄는 유일한 차이는 육안 검사 화면의 안내 문구입니다. "Strict Enforce: issues shown below will block sign-out until corrected"와 "Warn & Advisory: issues shown below don't block sign-out"입니다.
- 잉크 색상 사전을 불러올 수 없으면 게이트는 진행을 거부합니다(팔레트 사용 불가).
화면 텍스트와 게이트의 차이는 `open-questions/ch4.md`에 Pete를 위해 기재되어 있습니다.

**4. 선행 조건 및 종속 관계.** 이 확인은 기록된 잉크 색상을 활성 잉크 색상과 비교합니다. [잉크 색상](#screen-ink_colors)을 건너뛰면 기록된 모든 잉크 색상이 매핑되지 않은 것(심각도 3)이 되어 육안검사 완료가 차단됩니다. 시설은 [시설 사전](#screen-facility-dictionary)에서 가져옵니다.

**알려진 제한 사항.** 각인기 모니터는 Firebase가 구성되어 있으면 Firebase 컬렉션(`engraver_devices`)을 읽고, 그렇지 않으면 시뮬레이션된 장치를 표시합니다. Firebase는 운영 데이터베이스가 아니며 이 부분은 교체될 예정입니다. `src/pages/BatchManagement/`의 `README.md`에는 보존 보류 대기열이 구현되지 않았다고 아직 기재되어 있지만, 해당 페이지와 타일은 존재합니다. 배치는 구현됨입니다(`docs/architecture/CASE_WORKFLOWS_API.md`의 `IBatchService`).

## 디지털 병리 및 WSI 스캐너 통합과 뷰어 설정 {#ch4-digital-pathology}
Breadcrumb: 홈 > 구성 > 시스템

이 부분은 현재 PathScribe가 디지털 병리에 대해 제공하는 기능을 다룹니다. 범위를 정확히 이해하십시오. 두 가지가 있습니다. 첫째, [공급업체 통합](#screen-vendor_integrations)의 공급업체 사전이며, 이름과 웹 주소의 목록입니다. 둘째, [배치 관리](#screen-batch-management)의 슬라이드 스캔 대기열이며, 스캔 매니페스트를 인터페이스 엔진으로 보내고 상태를 돌려받습니다. **미구현:** 공급업체별 스캐너 드라이버 또는 공급업체 커넥터. 스캐너를 구성하는 화면은 없으며, [장비](#screen-equipment)에서 "슬라이드 스캐너" 종류의 장비로 이름을 지정하는 것이 전부입니다. PathScribe에는 슬라이드 뷰어가 없습니다. 스캔된 슬라이드는 스캐너의 미리 보기를 표시하고 검사실의 디지털 병리 애플리케이션에서 열리며, 이는 공급업체 통합의 **슬라이드 이미지**에서 설정합니다(배치 750). 모의 뷰어 페이지는 데모 전용입니다.

**3. 업무 목적 및 범위.** 검사실이 수행하는 품질 보증 활동을 정의합니다. 활동은 두 가지 원형 중 하나를 기반으로 만듭니다. **결과 검토**(케이스를 검토하고 등급을 매기는 활동, 예: 동결 대 최종 상관)와 **감독/배정**(케이스 수 또는 기간에 걸쳐 제공자를 감독하는 활동, 예: FPPE)입니다. **표준** 활동은 PathScribe가 검사실의 관할권에 맞게 선별한 것이며, 끌 수 없고 사용자 지정 활동으로 바꿀 수도 없으며, 샘플링, CAPA 트리거 및 이와 비슷한 설정만 구성할 수 있습니다. **사용자 지정** 활동은 검사실 자체의 활동입니다. 표준 또는 사용자 지정 활동을 복제하는 것이 더 빠른 방법이며, 검토 필드가 미리 구성되어 있기 때문입니다. CAPA는 자동으로 열리지 않습니다. 트리거는 QA 책임자에게 CAPA를 권고할 뿐이며, 책임자가 이를 확인하거나 기각합니다.

표준 검토 활동에는 다음이 포함됩니다: Frozen vs Final Correlation, Cytology-Histology Correlation, Abnormal/Critical Finding Confirmation, GYN Cytology Secondary Screening, Surgical Post-Sign-Out Peer Review, Surgical Biopsy-to-Resection Correlation, Pre-Sign-Out Peer Review, Clinical-Pathologic Correlation, Outside Consult Correlation. 표시되는 목록은 관할권에 따라 다릅니다.

**4. 선행 조건 및 종속 관계.** CAPA 트리거는 [검체 결함](#screen-deficiencies)의 결함 유형을 지정합니다. 예상 케이스 구성은 [세부 전문 분야](#screen-subspecialties)를 사용합니다.

Requires: [검체 결함](#screen-deficiencies), [세부 전문 분야](#screen-subspecialties)
Unlocks: [TAT 구성](#screen-tab-tat), [QA 추세 정책](#screen-qa_trend_policy)

| 행 | 환자 이름과 접수번호, 필드 레이블, 원본 텍스트, 사유 | 해당 없음 | 사유: 아직 입력된 답변이 없습니다, 텍스트에서 숫자를 찾을 수 없습니다, 숫자가 발견되었지만 이 파서가 신뢰하지 않는 텍스트로 둘러싸여 있습니다. | 해당 없음 |
| 변연 거리 (mm) | 숫자, 0 이상, 0.1 단위 | 해결하려면 필수 | 오류 "0 이상의 변연 거리를 입력하세요." | 공백 |

| 종료 | 버튼, 이어서 **이 필드에 거리를 제공할 수 없는 이유**가 있는 창 | 사유 필수 | **종료** 또는 취소. 사람과 사유가 기록됩니다. | 해당 없음 |
| 사례 열기 | 버튼 | 해당 없음 | 보고서를 열고 이 화면으로 돌아옵니다. | 해당 없음 |

**7. 권한.** 화면 열기: `screen:margin-exception-review:open`(Pathologist, Fellow, Resident, PA). 해결 또는 종료: `case:margin-exception:resolve`(고위험, 같은 역할).
**알려진 제한 사항.** 파서를 설정하는 구성 화면은 없으며, 규칙은 제품에 내장되어 있습니다.
