# 6단계: 인터페이스 엔진 및 외부 시스템 연동 {#ch7}

이 장에서는 PathScribe가 다른 시스템과 메시지를 주고받는 방식을 설명합니다. 다른 시스템에는 병원의 전자 의무기록(EHR), 검사실 정보 시스템(LIS), 참조 검사실, 청구 시스템, 등록처, 보고 도구가 포함됩니다. 또한 관리자가 이러한 교환을 모니터링하고 실패한 건을 처리하는 데 사용하는 화면도 다룹니다.

각 부분을 중심으로 프로젝트를 계획하기 전에 해당 부분의 상태를 확인하십시오. 이 단계의 상당 부분은 계약이 작성되어 있고 브라우저 측이 구현되어 있지만, 서버와 상대편 인터페이스 엔진은 아직 연결되지 않았습니다. 구현되지 않은 부분에는 해당 절에 **미구현** 또는 **예정**이라고 표시하고, 현재 존재하는 가장 가까운 기능을 함께 밝힙니다.

**이 장의 원칙.** 무엇을 언제 보낼지는 PathScribe가 결정합니다. 어떻게 보낼지는 인터페이스 엔진이 결정합니다. 여기에는 HL7 텍스트, 연결, 전송 구간의 재시도, 공급업체 고유의 표현이 포함됩니다. PathScribe는 공급업체의 필드 이름이나 코드를 번역하지 않으며, 어떤 EHR에 대해서도 인증된 커넥터라고 주장하지 않습니다.

## 6단계 설정 순서 {#ch7-order}
Breadcrumb: 홈 > 구성 > 시스템 > 통합

6단계는 대부분 선택 사항입니다. LIS, 등록처 피드, 보고 도구 없이 PathScribe를 단독으로 운영하는 검사실은 이 단계 전체를 건너뛰어도 됩니다. 사용하는 통합에 대해서만 아래 단계를 이 순서대로 수행하십시오. 각 단계에는 먼저 설정해야 하는 화면(1~5단계)이 명시되어 있으며, 같은 정보가 각 화면의 "설정 순서" 상자에도 표시됩니다.

1. [검체 코드 매핑](#screen-crosswalk): 수신 주문이 처리되도록 각 송신 시설의 자체 검체 코드를 귀 검사실의 검체 사전에 매핑합니다. 시설 사전과 검체 사전이 필요합니다.
2. [인터페이스 사전](#screen-interface_dictionary) (ForMedrixAI 직원 전용): 공급업체 고유의 필드를 기술합니다. 고객은 이 단계를 수행하지 않습니다. 번호가 빠짐없이 이어지도록 목록에 포함했습니다.
3. [LIS 수신(어시스트 모드)](#screen-assist_lis_polling): LIS가 케이스를 소유하고 PathScribe가 AI 초안으로 지원하는 검사실을 위한 단계입니다. AI 동작과 개요 라이브러리가 필요합니다.
4. [보고 피드 (Power BI)](#screen-bi_feed): 보고 도구가 PathScribe 데이터를 읽을 수 있게 합니다. 시설 사전에 수행 검사실 시설이 있어야 합니다.
5. [마이그레이션 필드 매핑](#screen-migration_field_mappings): 과거 데이터를 가져오기 전에 기존 시스템의 필드 이름을 매핑합니다.
6. [과거 데이터 마이그레이션 작업](#screen-migration-jobs): 기존 시스템의 파일을 가져오고 작업을 확인합니다. 5단계가 필요합니다.
7. [요청서 수집](#screen-requisition_ingestion): 일괄 스캔한 종이 요청서를 각 페이지의 바코드로 증례에 연결합니다. 스캐너의 드롭 폴더(또는 스캔을 보내는 시스템)가 필요합니다.

모니터링 화면([시스템 로그: 인터페이스](#screen-audit-interfaces), [인터페이스 엔진](#screen-interface-engines), [발신 인터페이스 DLQ](#screen-outbound-interface-dlq), [발신 전송 내역](#screen-outbound-dispatches), [발신 대기열](#screen-outbound-queue))과 테스트 도구([발신 인터페이스 메시지 미리보기](#screen-outbound_message_preview), [시뮬레이션 보낸 편지함](#screen-simulated_mail), [모의 인터페이스 엔진](#screen-mock-interface-engine), [모의 EMR](#screen-mock-emr))는 설정 단계가 아닙니다. 각 화면에는 `Reference, not part of setup`이라고 표시되어 있으며, 데이터를 표시하기 위해 무엇이 있어야 하는지가 나열되어 있습니다.

| 참조 검사실 의뢰 및 결과 수신 | 부분 구현 | 의뢰 매니페스트를 전송하고 결과 페이로드를 처리합니다. 아직 결과를 받는 수신 엔드포인트는 없습니다. [참조 검사실 인터페이스](#ch7-reflab)를 참조하십시오. |
| 인터페이스 모니터링, 오류 대기열 및 재처리 | 구현됨 (브라우저 측) | 화면과 해당 권한이 작동합니다. 엔진 하트비트와 엔진 측 재시도는 예정입니다. [모니터링](#ch7-monitoring)을 참조하십시오. |

## 인터페이스 엔진의 위치 {#ch7-architecture}
Breadcrumb: 홈 > 구성 > 시스템 > 통합

**상태:** 부분 구현

### "PathScribe 인터페이스 엔진"이라는 용어 {#ch7-pie-term}
Breadcrumb: 홈 > 구성 > 시스템 > 통합

이 가이드의 개요에서는 인터페이스 계층을 PathScribe 인터페이스 엔진(PIE)이라고 부릅니다. 이 이름은 제품, 제품의 화면, 설계 문서 어디에도 나타나지 않으며, 이 가이드는 제품 이름을 새로 만들지 않습니다. 제품에는 개요가 설명하는 일을 함께 수행하는 두 가지가 있습니다.

- **PathScribe 측.** 애플리케이션의 서비스가 무엇을 언제 보낼지 결정하고, JSON 메시지를 만들고, 대기열에 넣고, 결과를 기록하며, 관리자가 메시지를 다시 보내거나 보류하거나 해제할 수 있게 합니다. 이 장에서 클릭할 수 있는 모든 것은 이 측에 있습니다.
- **인터페이스 엔진.** 설계에서는 Mirth Connect의 오픈 소스 포크인 BridgeLink를 엔진으로 사용합니다. 엔진은 PathScribe의 JSON을 HL7(또는 다른 형식)으로 변환하고, 자체 메시지 저장소를 보유하며, 수신 시스템으로 전송하고, 회신을 받습니다. BridgeLink는 설계 문서(`INTERFACE_ENGINE_EDGE.md`)에서 쓰는 작업 명칭입니다. 채널 템플릿은 예정이며 구현되지 않았습니다.

### 엔진이 실행되는 위치 {#ch7-hosting}
Breadcrumb: 홈 > 구성 > 시스템 > 통합

엔진은 하나의 컨테이너 이미지이며 병원별로 선택하여 두 곳에서 사용합니다(결정 D6). ForMedrixAI가 테넌트의 지역에서 엔진을 호스팅하거나, 병원 내부의 가상 머신에 엔진을 설치할 수 있습니다. [인터페이스 엔진](#screen-interface-engines) 화면에는 각 엔진이 둘 중 어느 쪽인지(**호스팅** 또는 **현장**)가 표시됩니다. 이미지, 채널 템플릿, 상태 확인 엔드포인트는 서버 팀과 함께 예정되어 있습니다.

HL7 메시지는 SQL Server 메시지 버스로 이동하지 않습니다(결정 D1). API 서버는 `interface.dispatch` 유형의 작업으로 메시지를 엔진에 넘기며, 엔진은 HL7을 자체 메시지 저장소에 보관합니다.

### 현재 실행되는 것과 예정된 것 {#ch7-today}
Breadcrumb: 홈 > 구성 > 시스템 > 통합

| 구성 요소 | 상태 | 사용자에게 의미하는 바 |
|---|---|---|
| 송신 메시지, JSON 봉투 | 구현됨 (브라우저 측) | 브라우저는 `{queueEntryId, transactionType, dispatchedAt, payload}`를 빌드 설정 `VITE_INTERFACE_RECEIVER_ENDPOINT`의 주소로 전송합니다. 운영 빌드에서는 주소가 `https`여야 하며, 주소가 없거나 일반 HTTP이면 아무것도 전송하기 전에 거부됩니다. 대기 시간은 15초입니다. |
| 전송된 것으로 간주하는 기준 | 구현됨 (브라우저 측) | 2xx 응답이면 메시지가 전송된 것으로 표시됩니다. 아직 HL7 확인 응답(ACK)은 없습니다. 시간 초과, 엔진에 연결할 수 없음, 거부는 화면에서 서로 다른 세 가지 오류입니다. |
| 데모 빌드 | 데모 | 엔진 주소가 설정되지 않으면 모의 엔진이 모든 메시지를 받아 목록에 보관합니다. [모의 인터페이스 엔진](#screen-mock-interface-engine)을 참조하십시오. |
| 기기에서 오는 수신 이벤트 | 구현됨 (브라우저 측) | 카세트 엔진용 웹훅이 4개 있습니다. 블록 예외, 카세트 전송 결과, 재료 위치, 각인기 상태입니다. `X-API-Key` 헤더의 공유 비밀 값을 사용하며, HMAC 서명은 선택 사항입니다. |
| 수신 HL7 메시지 | 미구현 | ADT 및 환자 관리 처리기는 있으며 테스트되었지만, 실제 HL7 메시지를 받아 이를 호출하는 구성 요소는 없습니다. |
| 엔진용 서버 엔드포인트 (`POST /api/interface/inbound`, `POST /api/interface/outbound-acks`, `POST /api/interface/heartbeat`, `GET /api/interface/engines`) | 예정 | 계약(2e 단계)으로 작성되어 있습니다. 인계, 확인 응답으로 확정되는 결과, 재시도 구간, 데드 레터, 엔진 상태를 추가합니다. |
| 테넌트별 엔진 자격 증명 | 예정 | 테넌트 엔진마다 OAuth2 클라이언트 자격 증명 또는 상호 TLS를 사용합니다. [FHIR R4 및 OAuth2](#ch7-fhir)를 참조하십시오. |

**예정된 재시도 구간.** 계약에 따르면 수신 메시지는 10초, 30초, 1분, 5분, 15분 동안 대기하며 24시간 후에 데드 레터가 됩니다. 송신 메시지는 1분, 5분, 15분, 60분에 다시 보내고, 이후 24시간 동안 매시간 다시 보냅니다. 등록처 제출 건은 72시간 동안 보관합니다. AA 확인 응답이 전송됩니다. CA는 전송되거나 애플리케이션 확인 응답을 기다립니다. AR과 CE는 구간 내에서 재시도하며, AE와 CR은 즉시 실패합니다. 데드 레터가 된 결과는 같은 케이스의 이후 메시지를 보류합니다. 이 중 현재 실행되는 것은 없습니다. 현재는 전송에 실패하면 관리자가 다시 보낼 때까지 대기합니다.

### 저장되지만 사용되지 않는 시설 인터페이스 설정 {#ch7-facility-settings}
Breadcrumb: 홈 > 구성 > 시스템 > 통합

시설 편집기(1단계, [시설 사전](#screen-facility-dictionary))에는 **LIS 연동** 탭이 있습니다. 이 탭에는 엔진 주소, HL7 버전, 인증 유형(없음, 기본, OAuth2 또는 API 키), 자격 증명이 프로비저닝되었는지 나타내는 플래그, LIS가 케이스 상태를 소유하는지 여부, PathScribe가 최종 확정 후 작업을 허용하는지 여부, 송신 시설과 수신 시설의 라우팅 식별자, 송신 채널 재정의가 저장됩니다. 이 설정은 시설과 함께 저장됩니다. 현재 이 설정을 읽는 전송 경로는 없으며, 메시지는 위에서 설명한 배포 수준의 단일 주소로 전송됩니다. 자격 증명은 저장되지 않고 예/아니요 플래그만 저장됩니다.

## 수신 및 송신 HL7 v2.x {#ch7-hl7}
Breadcrumb: 홈 > 구성 > 시스템 > 통합

**상태:** 부분 구현

### 메시지 유형 {#ch7-hl7-types}
Breadcrumb: 홈 > 구성 > 시스템 > 통합

메시지 유형을 켜거나 끄는 화면은 없습니다. 아래 유형은 제품에서 고정되어 있습니다. 이 부분에는 코드가 지원하는 것만 나열합니다. 나열되지 않은 것은 지원되지 않습니다.

**송신.** PathScribe는 다음 트랜잭션 유형을 대기열에 넣습니다. "PathScribe builds HL7"로 표시한 3종을 제외한 모든 유형의 HL7은 엔진이 만듭니다.

| 트랜잭션 유형 | 전달하는 내용 | HL7 형태 |
|---|---|---|
| `A08` | 환자 인구통계 정보 갱신 | 엔진이 ADT^A08을 만듭니다. 성별은 PID-8에 M, F, U 또는 미확정을 뜻하는 A로 전송됩니다(코드 A는 수신 시스템과 확인되기 전까지의 가정입니다). 영국 사이트의 NHS 코드는 M은 1, F는 2, I는 9, U는 X입니다. |
| `A40` | 환자 병합 | 엔진이 ADT^A40을 만듭니다 |
| `A47` | 환자 식별자 변경 | 엔진이 ADT^A47을 만듭니다 |
| `ORU_R01` | 최종, 수정 또는 정정된 병리 결과 | 엔진이 ORU^R01을 만듭니다. 미국 전자 병리 보고(7단계)의 경우 PathScribe가 ORU^R01 v2.5.1을 직접 만듭니다. |
| `LIS_SYNC` | LIS용 케이스 데이터와 어시스트 모드 케이스의 시놉틱 결과 | 엔진이 만듭니다 |
| `ORDER_CREATED` | 새 주문 | 엔진이 만듭니다 |
| `ACCESSION_EVENT` | 접수된 주문 또는 접수 결함 | 엔진이 만듭니다 |
| `REGISTRY_REPORT`, `CANCER_REGISTRY_REPORT` | 등록처 제출 (7단계) | 엔진이 만듭니다. 확인 응답이 돌아옵니다. |
| `REPORT_DELIVERY` | e-팩스 또는 파일 전달용 서명된 보고서 PDF | 엔진 또는 전달 서비스 |
| `PRINT_JOB` | 엔진이 인쇄할 보고서 PDF | 엔진 |
| `REFERRAL_MANIFEST` | 참조 검사실로 보내는 의뢰 배치의 매니페스트 | 엔진이 만듭니다. 결과가 돌아옵니다. |
| `MOLECULAR_ORDER` | 분자 검사 주문 또는 기기 주문 | 엔진이 만듭니다 |
| `WSI_SCAN_MANIFEST` | 전체 슬라이드 스캔 배치에 로드된 슬라이드 | 엔진이 만듭니다. 슬라이드 스캔 상태가 돌아옵니다. |
| `BLOCK_ORDER` | 포매 또는 염색 기기를 위한 블록 하나의 염색 주문 | PathScribe가 HL7을 만듭니다: ORM^O01 |
| `SLIDE_ORDER`, `SPECIMEN_LABEL` | 슬라이드 주문, 검체 용기 라벨 | 엔진이 만듭니다 |

| `CHARGE_DFT` | 청구 시스템으로 보내는 수가 | PathScribe가 HL7을 만듭니다: DFT^P03 |
| `CHARGE_JSON` | JSON 청구 웹훅으로 보내는 수가 | JSON, HL7 없음 |
| `FINANCIAL_CLASS` | 청구 엔진용 재무 분류 페이로드 | 형식이 정해질 때까지 미리보기 페이로드 |
| `CRITICAL_ALERT` | 출시 후 중대 알림 채널 | 연결되지 않았습니다. 현재 이를 생성하는 것은 없습니다. |

따라서 개요에서 말하는 "ORM"은 PathScribe가 기기로 보내는 블록 주문용으로 만드는 ORM^O01입니다. PathScribe는 EHR이나 LIS용 ORM을 직접 만들지 않습니다. 주문 생성 메시지가 어떤 HL7이 되는지는 엔진이 결정하며, 메시지 유형을 추가하는 화면은 없습니다.

**수신.** 이 처리기들은 애플리케이션에 있습니다. 위에서 설명한 기기 웹훅을 제외하면 실제 리스너에 연결된 것은 없습니다. 데모 빌드에서는 [모의 인터페이스 엔진](#screen-mock-interface-engine)으로 붙여 넣은 메시지를 이 처리기에 통과시켜 볼 수 있습니다.

| 계열 | 메시지 | 상태 |
|---|---|---|
| 입원, 퇴원, 전동 (`adtParser.ts`) | A01, A03, A04, A08, A02, A09, A10, A05, A06, A07, A11, A12, A13, A31 | 처리기 구현됨, 리스너 없음 |
| 환자 관리 (`patientManagementParser.ts`) | A40 병합, A24 연결, A47 식별자 변경, A43 이동 | 처리기 구현됨, 리스너 없음. 일치시킬 수 없는 메시지는 추측하지 않고 인터페이스 예외로 대기열에 넣습니다. |
| 방문 변경 (`processVisitMessage.ts`) | A45, A50, A34 | 처리기 구현됨, 리스너 없음 |
| LIS 주문 상태 (어시스트 어댑터) | ORU^R01, ORM^O01, OML^O21 | 상태 전용입니다. [LIS 수신(어시스트 모드)](#screen-assist_lis_polling)에 붙여 넣을 수 있습니다. |
| JSON 이벤트 | HPV 결과, 블록 예외, 재료 위치, 의뢰 결과, 분자 검사 실행 결과, 전체 슬라이드 스캔 상태 | 처리기 구현됨, 기기 웹훅이 유일한 실제 경로 |

**수신 주문은 HL7에서 파싱되지 않습니다.** 주문 접수 서비스는 ORM 메시지가 아니라 구조화된 주문을 받으므로, EHR에서 오는 실제 HL7 주문은 현재 허용되지 않습니다. [검체 코드 매핑](#screen-crosswalk)은 주문이 서비스에 도달한 뒤 주문의 코드를 해석합니다.

**공급업체 어댑터.** Cerebro와 Vantage용 어댑터는 의도적으로 아무 동작도 하지 않는 스텁입니다.

### 검체 코드 매핑 {#screen-crosswalk}
Breadcrumb: 홈 > 구성 > 시스템 > 통합 > 주문 유형 및 수신 규칙

**상태:** 구현됨

**1. 탐색:** 구성 탭 **시스템** > 그룹 **통합**
**2. 유지 관리 항목:** 주문 유형 및 수신 규칙(메뉴 이름). 화면의 제목은 **검체 코드 매핑**입니다.

**3. 업무 목적 및 범위.** 송신 시스템은 검체에 자체 코드를 사용하며, 같은 코드가 송신 시스템마다 다른 의미를 가질 수 있습니다. 이 화면은 각 송신 시설의 코드를 검체 사전 항목 하나에 매핑합니다. 들어오는 모든 주문은 이 표와 대조됩니다. 일치하는 항목이 없으면 PathScribe는 주문을 차단하지 않습니다. **자동 학습됨 — 검토 대기 중**으로 표시된 항목을 만들고, 주문이 진행될 수 있도록 보류 중인 검체 사전 항목을 만들며, 담당자가 해결하도록 `unmapped_order_code` 유형의 인터페이스 예외를 대기열에 넣습니다. 이 화면에서 자동 학습된 항목을 검토하거나, 알려진 코드를 학습할 필요가 없도록 실제 항목을 미리 추가합니다.

### LIS 수신(어시스트 모드) {#screen-assist_lis_polling}
Breadcrumb: 홈 > 구성 > 시스템 > 통합 > LIS 수신(어시스트 모드)

**상태:** 부분 구현

**1. 탐색:** 구성 탭 **시스템** > 그룹 **통합**
**2. 유지 관리 항목:** LIS 수신(어시스트 모드)

**3. 업무 목적 및 범위.** 어시스트 모드에서는 외부 LIS가 케이스를 소유합니다. LIS의 업데이트는 폴링, HL7 v2 메시지, JSON 웹훅의 세 가지 방식으로 PathScribe에 도달하며, 세 가지 모두 하나의 수신 대기열을 거칩니다. LIS가 육안 검사 완료를 보고하면 AI가 시놉틱 템플릿을 선택하고 육안 소견 텍스트에서 작성할 수 있는 필드의 초안을 작성합니다. LIS가 현미경/진단 완료를 보고하면 진단을 바탕으로 나머지 초안을 작성합니다. 이 화면에는 설정, 붙여 넣은 메시지를 위한 테스트 상자, 수신 대기열, 실행 로그가 있습니다.

**구현된 것과 구현되지 않은 것.** 구현됨: 설정, 상태 매핑, 테스트 상자, 재시도가 있는 수신 대기열, 실행 로그, AI 초안 작성 규칙. 데모에서 시뮬레이션됨: 일정(앱이 열려 있고 폴링이 켜져 있는 동안 저장된 간격으로 폴링하며, 화면에는 마지막 실행과 다음 실행이 있는 **시뮬레이션 일정** 안내가 표시됩니다)과 **지금 조회**가 요청하는 LIS. 구현되지 않음: HL7 또는 웹훅 메시지를 받는 실제 리스너와 조회할 LIS의 주소를 입력하는 필드. 화면에는 그러한 필드가 없습니다.

**4. 사전 요건 및 종속성.** AI 단계는 AI 동작 스위치와 시놉틱 템플릿을 사용합니다. **AI 동작 설정에서 AI 꺼짐**이 적용되면 업데이트는 케이스 텍스트만 변경하고 초안은 만들지 않습니다. 어시스트 모드의 케이스만 처리되며, 어시스트 모드가 아닌 케이스는 **어시스트 케이스 아님**이라는 결과로 건너뜁니다.

어댑터가 읽는 내용입니다. HL7 메시지는 ORU^R01, ORM^O01 또는 OML^O21이어야 하며 다른 유형은 거부됩니다. OBR 세그먼트마다 업데이트가 하나씩 만들어집니다. 접수번호는 OBR-3이며, 없으면 OBR-2, 그것도 없으면 ORC-3입니다. 상태는 ORC-5이며, 없으면 OBR-25입니다. 시간은 OBR-22이며, 없으면 MSH-7입니다. 오프셋이 없는 시간은 UTC로 읽으므로 LIS에 오프셋을 보내도록 요청하십시오. 텍스트는 OBX-3의 LOINC 코드에 따라 OBX-5에서 가져옵니다. `22634-0`은 육안 소견, `22635-7`은 현미경 소견, `22637-3`은 최종 진단입니다. JSON 본문은 객체 하나 또는 목록이며, `accession`, `status`, `updatedAt`(ISO 8601)은 필수이고 `grossText`, `microscopicText`, `diagnosisText`, `placerOrderNumber`, `fillerOrderNumber`는 선택입니다. 주문 번호는 시놉틱 결과에 그대로 반영됩니다.

### [FORMEDRIXAI INTERNAL ONLY] 인터페이스 사전 {#screen-interface_dictionary}

> 🔒 **ForMedrixAI 내부 제한 설정**
> **범위:** 내부 서비스 및 배포 담당 직원 전용.
> **설명:** 공급업체 프로필은 공급업체 고유의 HL7, JSON 또는 FHIR 메시지에서 어떤 필드를 확장 필드로 케이스에 복사할지 결정합니다. 잘못되었거나 테스트 없이 변경된 프로필은 케이스에 잘못된 값을 넣거나 필수 값을 빠뜨릴 수 있으며, 케이스 기록은 의무기록입니다. 프로필은 ForMedrixAI 직원만 작성하고 게시하므로 각 프로필은 실제 샘플로 테스트되고 버전이 관리됩니다. 이를 보호하는 세 가지 권한은 플랫폼 전용이며 Superadmin 역할이 보유하고 병원이 부여할 수 없습니다. 이 권한이 없는 사람에게는 이 섹션이 표시되지 않습니다.

**상태:** 부분 구현

**1. 탐색:** 구성 탭 **시스템** > 그룹 **통합**
**2. 유지 관리 항목:** 인터페이스 사전

**3. 업무 목적 및 범위.** 인터페이스 사전은 공급업체 프로필을 보관합니다. 프로필은 하나의 공급업체 또는 장치와 하나의 메시지 유형에 대해 공급업체의 각 필드가 메시지의 어디에 있는지, 그리고 케이스의 어떤 확장 필드(`ext.name`)가 되는지를 지정하며, 선택적으로 변환, 기본값, 코드 변환, 필수 플래그를 지정할 수 있습니다. 프로필은 초안, 테스트, 게시의 정해진 수명 주기를 거치며, 이후 되돌리거나 끌 수 있습니다. 같은 매핑 엔진이 실제 메시지를 읽도록 되어 있으므로, 프로필로 코드 릴리스 없이 공급업체 필드를 추가할 수 있습니다.

**구현된 것과 구현되지 않은 것.** 구현됨: 프로필 만들기, 매핑 편집, 샘플 메시지로 하는 테스트, 게시, 되돌리기, 끄기, 범위 보호. 시뮬레이션됨: **케이스에 적용** 패널로, 붙여 넣은 메시지를 케이스에 적용하여 공급업체 필드 패널을 볼 수 있게 합니다. 배너에는 "이 빌드에서는 공급업체로부터 아무것도 수신되지 않습니다."라고 표시됩니다. 공급업체 프로필은 미리 제공되지 않으므로 목록은 비어 있는 상태로 시작합니다. 프로필은 확장 필드만 채울 수 있습니다. 그 밖의 것은 코드 릴리스가 필요합니다(아래의 범위 표 참조).

**4. 사전 요건 및 종속성.** 이 가이드에는 없습니다. 테스트하려면 공급업체의 샘플 메시지가 필요합니다.

**7. 권한.** 세 가지 모두 플랫폼 전용입니다. `platform:interface-dictionary:manage`(만들기, 편집, 테스트, 끄기, 되돌리기), `platform:interface-dictionary:publish`(게시, manage 필요), `platform:interface-dictionary:simulate`(데모에서 케이스에 적용, manage 필요)입니다. Superadmin 역할만 이 권한을 가집니다. 병원은 이를 자체 역할에 부여할 수 없습니다. manage 권한이 없으면 이 섹션은 숨겨집니다. 거부된 변경에는 "공급업체 프로필은 ForMedrixAI 직원만 변경할 수 있습니다."라고 표시됩니다.

**알려진 제한.** 공급업체 프로필은 미리 제공되지 않으며, 아직 프로필을 통해 읽는 실제 메시지는 없습니다. 코드의 섹션 머리글은 이를 Message Mapper라고 부르지만 그러한 메뉴 이름은 없습니다.

## FHIR R4 엔드포인트 및 OAuth2 클라이언트 자격 증명 {#ch7-fhir}
Breadcrumb: 홈 > 구성 > 시스템 > 통합

**상태:** 미구현

PathScribe에는 FHIR R4 엔드포인트가 없습니다. FHIR 서버를 게시하지 않고, 다른 시스템의 FHIR 리소스를 받지 않으며, FHIR 기본 주소, 클라이언트 ID, 클라이언트 시크릿, 토큰 주소를 설정하는 화면도 없습니다. OAuth2 클라이언트 자격 증명 설정 화면도 없습니다. 둘 중 어느 것에라도 의존하는 가동 시작을 계획하지 마십시오.

문의가 무엇에 관한 것인지 알 수 있도록, 이에 가장 가까운 것을 정리했습니다.

| 항목 | 내용 | 상태 |
|---|---|---|
| FHIR 소스용 케이스 서비스 (`FHIRCaseService.ts`) | FHIR 서버에서 케이스를 읽기 위한 뼈대 코드입니다. 기본 주소는 자리 표시자이고 액세스 토큰을 가져오는 함수는 예외를 발생시킵니다. 어떤 화면이나 설정에도 연결되어 있지 않습니다. | 미구현 |
| [인터페이스 사전](#screen-interface_dictionary)의 메시지 형식으로서의 FHIR | `Observation`과 같은 FHIR 리소스에 대해 공급업체 프로필을 작성할 수 있으며, 테스트는 붙여 넣은 샘플을 읽습니다. 공급업체의 FHIR 메시지를 받는 것은 없습니다. | 부분 구현, ForMedrixAI 전용 |
| 시설 편집기의 인증 유형 | **LIS 연동** 탭에서 시설의 엔진 연결에 대한 인증 유형으로 `OAuth2`를 선택할 수 있습니다. 저장되는 선택값일 뿐이며 이를 읽는 코드는 없습니다. | 저장만 됨 |
| 테넌트별 엔진의 OAuth2 클라이언트 자격 증명 또는 상호 TLS | 엔진이 PathScribe API에 자신을 증명하는 방법에 대한 계약입니다(`INTERFACE_ENGINE_EDGE.md`). | 예정 |
| OpenID Connect(OIDC)를 통한 직원 로그인 | 시스템 간 메시지가 아니라 사람을 위한 싱글 사인온입니다. 1단계에서 다룹니다. | 구현됨 (브라우저 측) |
| [보고 피드 (Power BI)](#screen-bi_feed)용 토큰 | PathScribe가 발급하여 한 번만 표시하고 지문 형태로만 보관하는 베어러 토큰입니다. OAuth2가 아닙니다. | 부분 구현 |

[모의 EMR](#screen-mock-emr) 페이지에는 "Production uses FHIR R4 API to sync with LIS"라는 안내 문구가 있습니다. 코드에는 이 문장을 뒷받침하는 것이 없습니다. 설계 의도로 간주하십시오.

## EHR 연동: Epic, Cerner, MEDITECH, AthenaHealth {#ch7-ehr}
Breadcrumb: 홈 > 구성 > 시스템 > 통합

**상태:** 미구현

PathScribe에는 인증 여부와 관계없이 어떤 EHR용 커넥터도 없습니다. 어떤 공급업체의 마켓플레이스에도 등록되어 있지 않으며, 이 가이드의 근거로는 어떤 공급업체의 검증도 통과하지 않았습니다. EHR이 보내거나 받는 모든 것은 병원의 인터페이스 팀이 구성하는 인터페이스 엔진을 거치며, PathScribe는 [메시지 유형](#ch7-hl7-types)에 있는 메시지만 봅니다. 고객에게 PathScribe를 "Epic 인증" 또는 "Cerner 인증" 등으로 설명하지 마십시오.

| EHR | PathScribe에 있는 것 | PathScribe에 없는 것 |
|---|---|---|
| Epic | **Epic Beaker**라는 이름의 식별자 형식 프리셋(접수번호와 2D 슬라이드 바코드 패턴)입니다. 1단계의 시설 편집기 식별자 형식 탭에서 설정합니다. | 커넥터, Epic 전용 메시지 프로필, 인증, FHIR 앱 등록. |
| Cerner | **Cerner PathNet**이라는 이름의 식별자 형식 프리셋입니다. | 위와 같습니다. |
| MEDITECH | **MEDITECH**라는 이름의 식별자 형식 프리셋입니다. | 위와 같습니다. |
| AthenaHealth | 없습니다. 이 이름은 코드, 화면, 설계 문서 어디에도 나타나지 않습니다. | 모든 것. |

같은 프리셋 목록에는 Generic, CoPath, Sunquest, 사용자 지정도 있습니다. 프리셋은 스캔 상자가 인식하는 접수번호와 바코드 패턴만 결정합니다. 어떤 것과도 메시지를 교환하지 않습니다.

**현재 EHR 연동의 모습.** EHR은 엔진을 통해서만 PathScribe에 도달할 수 있으며, [메시지 유형](#ch7-hl7-types)의 송신 메시지(결과, 환자 업데이트, 주문 이벤트, 접수 이벤트)로서, 그리고 아직 실제 리스너에 연결되지 않은 수신 처리기로서 도달합니다. [인터페이스 사전](#screen-interface_dictionary)에는 어떤 EHR에 대해서도 미리 제공된 공급업체 프로필이 없습니다. [검체 코드 매핑](#screen-crosswalk)은 주문이 주문 접수 서비스에 도달한 뒤 EHR의 검체 코드를 매핑합니다. 환자 신원에 대한 권한은 EHR이 가집니다. 일치시킬 수 없는 A40, A24, A47 또는 A43 메시지는 추측하지 않고 담당자가 처리하도록 인터페이스 예외로 대기열에 넣습니다. [시스템 로그: 인터페이스](#screen-audit-interfaces)를 참조하십시오.

## 참조 검사실 인터페이스 {#ch7-reflab}
Breadcrumb: 홈 > 구성 > 시스템 > 통합

**상태:** 부분 구현

참조 검사실은 분자 검사나 외부 의뢰 면역조직화학 검사처럼 외부 위탁 검사를 위해 검체를 보내는 시설입니다. PathScribe는 매니페스트로 하는 의뢰 발송과 결과 메시지로 하는 결과 수신을 지원합니다. 송신 측은 구현되어 있으며, 수신 측에는 처리기는 있지만 엔드포인트는 없습니다.

"참조 검사실 인터페이스"라는 화면은 없습니다. 설정은 이미 있는 여러 화면에 나뉘어 있습니다.

1. **검사실을 시설로 만듭니다.** [시설 사전](#screen-facility-dictionary)에서 검사실을 추가하고 **참조 검사실(발신 의뢰 대상)** 역할을 지정합니다. 이 역할이 있어야 의뢰 배치의 대상으로 선택할 수 있습니다. 해당 역할이 있는 활성 시설만 표시됩니다.
2. **수행하는 검사와 연결합니다.** [진단 카탈로그](#screen-stains)에서 **분자** 검사에는 해당 검사를 수행하도록 승인된 참조 검사실과 그중 기본 검사실이 나열됩니다. 기본 검사실은 승인된 검사실 중 하나여야 합니다. 이 연결은 분자 범주에만 유지되며, 해당 검사의 추가 주문은 기본 검사실을 채우고 승인된 검사실만 표시합니다.
3. **발송합니다.** 의뢰 배치는 [배치 관리](#screen-batch-management)에서 처리 노드 **외부 의뢰**와 대상 시설을 지정하여 만듭니다. 배치가 대조를 완료하면 PathScribe는 `REFERRAL_MANIFEST` 메시지를 대기열에 넣고 추적 기록을 자동으로 만듭니다. 여기서 발생한 실패가 배치 자체의 완료를 막지는 않습니다. 매니페스트에는 배치 ID, 마스터 바코드, 대상 시설, 요청한 검사, 우선순위(**STAT** 또는 **Routine**), 항목(표시 ID, 재료 유형, 케이스 접수번호, 검체 라벨), 그리고 외부 의뢰 분자 검사 주문이 들어 있습니다. 무엇을 언제 보낼지는 PathScribe가 결정하고 전송 방식은 엔진이 결정합니다.
4. **발송을 확인합니다.** 메시지는 [발신 대기열](#screen-outbound-queue)에서는 피드 **의뢰**에, [발신 인터페이스 DLQ](#screen-outbound-interface-dlq)에서는 대기열 **의뢰 송장**에 나타나며, 실패한 메시지는 여기서 다시 보냅니다.
5. **결과를 수신합니다.** 결과 메시지(`ReferralResultEventPayload`)에는 배치 ID와 **discrete** 결과(텍스트) 또는 **pdf_attachment**(PDF 링크) 중 하나가 들어 있으며 둘 다 들어 있는 경우는 없고, 선택적으로 외부 의뢰 분자 검사 주문별 결과도 들어 있습니다. 처리기는 형식을 확인하고, 배치를 찾고, 결과를 기록하고, 배치를 **result_received**로 표시한 다음 코드화된 결과를 분자 검사 주문에 적용합니다. 배치의 상태는 발송됨, 운송 중, 전달됨, 결과 수신됨의 순서로 앞으로만 이동합니다. 사람이 운송 중과 전달됨을 직접 설정할 수 있으며, 결과 수신됨은 결과가 도착할 때만 설정됩니다.

**구현되지 않은 것.** 결과 메시지를 받는 엔드포인트가 없으므로 참조 검사실에서 결과가 저절로 도착하지 않습니다. 처리기는 처리한 메시지 ID를 메모리에만 기억하므로 재시작하면 잊어버립니다. 처리기는 적용됨, 이미 적용됨, 추적 정보를 찾을 수 없음, 잘못된 페이로드의 네 가지 응답 중 하나를 반환합니다. [모의 인터페이스 엔진](#screen-mock-interface-engine)에는 의뢰 결과용 테스트 샘플이 없습니다. 참조 검사실 고유의 표현(검사 이름과 결과 코드)은 PathScribe가 번역하지 않으며 엔진이 담당합니다.

### 재처리 규칙 한눈에 보기 {#ch7-reprocessing}
Breadcrumb: 홈 > 품질 및 준수

실패한 메시지는 폐기되지 않으며, 현재는 사람이 버튼을 누르지 않으면 아무것도 다시 전송되지 않습니다. 아래 규칙은 코드가 강제하는 내용입니다.

| 상황 | 표시되는 위치 | 할 수 있는 작업 | 권한 |
|---|---|---|---|
| 수신 환자 메시지를 일치시킬 수 없음 (A40, A24, A47, A43) | [시스템 로그: 인터페이스](#screen-audit-interfaces), 인터페이스 예외 | 검토하고, 환자를 직접 연결하거나 케이스를 이동하거나, 기각합니다. 메시지는 추측하지 않습니다. | 전용 권한 없음. 해당 화면의 알려진 제한을 참조하십시오. |
| 수신 주문 코드가 검체 사전과 일치하지 않음 | 인터페이스 예외, 유형 `unmapped_order_code` | **매핑 및 연결**로 [검체 코드 매핑](#screen-crosswalk) 항목을 만들거나, 기각합니다. | 항목에는 `config:crosswalk:manage` |
| 송신 메시지의 전송 실패 | [발신 인터페이스 DLQ](#screen-outbound-interface-dlq) 및 [발신 대기열](#screen-outbound-queue)의 **실패** | **전송 재시도** 또는 **지금 전송**으로 엔진에 다시 보냅니다. | `interface:outbound:resend` |
| 메시지를 아직 보내지 않아야 함 | 발신 대기열, **대기 중** 또는 **실패** | 사유를 입력하여 **보류**한 다음 **해제**합니다. 보류된 메시지는 다른 어떤 작업으로도 전송되지 않습니다. 재시도하면 "발신 대기열에서 보류됨: 먼저 그곳에서 해제하세요."라고 표시됩니다. | `interface:outbound:hold`, `interface:outbound:release` |
| 자동 재시도 이후에도 메시지가 실패함 | 발신 대기열, **재시도 소진** | **재시도**, 또는 청구 항목의 경우 **청구 철회**. | `interface:outbound:resend`, `interface:outbound:retract` |
| 등록처가 제출을 거부함 | 발신 대기열, **거부됨** | 사유를 입력하여 **재시도**(재제출)하거나, 사유를 입력하여 **보고 대상 아님으로 표시**합니다. | `interface:outbound:resend`, `interface:outbound:mark-not-reportable` |
| 수가를 일찍 내보내거나 취소해야 함 | 발신 대기열, 청구 항목 | **지금 해제** 또는 **청구 철회**. | `interface:outbound:override-release`, `interface:outbound:retract` |
| 보고서 인쇄, 팩스 또는 파일 전달이 재시도 후에도 실패함 | 발신 인터페이스 DLQ 맨 위의 전달 예외 | 해당 대기열(인쇄 대기열 또는 보고서 전달)에서 다시 보냅니다. 성공하면 목록에서 사라집니다. | 보고서 전달에는 `interface:outbound:resend` |
| 대기열에 있던 수가가 실패함 | 시스템 로그의 발신 DLQ 하위 탭, 재무 (7단계) | [시스템 로그: 재무](#screen-audit-financial)를 참조하십시오. | 해당 화면 참조 |

**기본 제공 역할.** Admin은 `interface:outbound:*` 권한 전체와 `interface:engine-status:view`, `jobs:server-job:view`를 가집니다. Lab Director는 이 중 어느 것도 가지지 않으며 발신 대기열 화면이 없습니다. QA Reviewer는 감사 로그 화면과 내보내기만 열 수 있습니다. Superadmin은 모든 권한을 가집니다 (단, `config:ai-prompt:approve`는 직무 분리를 위해 제외됩니다). 기본 제공 Interface Analyst 역할은 없습니다. 병원이 직접 만들어 원하는 권한을 부여합니다(시드 파일에 그렇게 나와 있습니다).

**재전송이 하는 일.** 재전송은 기록에서 메시지를 다시 만들어 전송합니다. 참조하는 기록이 더 이상 없으면 아무것도 전송되지 않으며 화면에 "전송되지 않음: 메시지를 만들 수 없습니다"라고 표시됩니다. 아직 보고서 PDF가 없는 결과는 전송되지 않고 보류되며, 이후 재시도 시 PDF와 함께 전송됩니다. 메시지를 변경하는 모든 작업은 메시지당 하나의 항목으로 감사 로그에 기록되며, 감사 텍스트에는 환자 이름이 포함되지 않습니다. 전송 구간의 재시도(엔진이 연결을 다시 시도하는 것)는 PathScribe가 아니라 엔진이 담당합니다.

### 시스템 로그: 인터페이스 {#screen-audit-interfaces}
Breadcrumb: 홈 > 품질 및 준수 > 시스템 로그 > 인터페이스 로그

**상태:** 구현됨

**1. 탐색:** 홈 > **품질 및 준수** > **시스템 로그** > 탭 **인터페이스 로그**(화면의 탭 이름), 주소는 `/audit?tab=interfaces`입니다.
**2. 유지 관리 항목:** 시스템 로그: 인터페이스

**3. 업무 목적 및 범위.** 다른 시스템과의 경계에서 무엇이 잘못되었는지 확인하는 단일 장소입니다. 하위 탭이 다섯 개 있습니다. **인터페이스 예외**(처리할 수 없었던 수신 메시지), **발신 인터페이스 DLQ**(실패했거나 대기 중인 송신 메시지), **발신 전송 내역**(주문 생성 이벤트의 이력), **인쇄 대기열**, **엔진**(인터페이스 엔진 상태이며 `interface:engine-status:view`가 있을 때만 표시됩니다)입니다. 하위 탭 위의 한 줄은 엔진을 요약하며 한 번의 클릭으로 **엔진**을 엽니다. 탭에는 대기 중인 예외의 수가 배지로 표시됩니다.

### 발신 대기열 {#screen-outbound-queue}

**상태:** 구현됨

**1. 탐색:** 홈 > **품질 및 준수** > **발신 대기열**, 주소는 `/outbound-queue`입니다.
**2. 유지 관리 항목:** 발신 대기열

**3. 업무 목적 및 범위.** 모든 발신 메시지를 한곳에 모아 보류, 해제, 재시도를 할 수 있고, 등록기관이 반려한 건을 수정할 수 있습니다. 열 개의 피드(결과, 환자 ADT, 접수, LIS 동기화, 청구, 보고서 전달, 세포병리 결과, 의뢰, 분자 오더, 등록기관)를 하나로 모으며, 각 메시지의 대상(인터페이스 엔진, 청구 시스템, LIS 파트너, 전달 서비스 또는 등록기관), 엔진이 사용하는 전송 방식(REST + mTLS, SFTP, 포털 업로드, PHIN-MS, 직접 TCP 또는 HTTPS API이며, 대상 레이블의 일부로만 표시됩니다), 상태를 보여 줍니다. 무엇을 언제 해제할지는 PathScribe가 결정하고, 전송은 엔진이 수행합니다.

**4. 사전 요건 및 종속성.** 대기열은 메시지가 나가는 시점과 보고 기한을 [전달 일정](#screen-delivery_schedules)에서 읽습니다. 수행 시설 자체의 일정이 우선하고, 없으면 기업의 일정, 그것도 없으면 피드의 기본값을 따릅니다. 일정이 없으면 메시지는 피드의 기본값을 따릅니다. 청구 항목은 청구 해제 설정도 따르고 등록기관 항목은 등록기관 설정을 따르며, 둘 다 7단계에 있습니다.

거부는 개수로 보고됩니다. 허용되지 않음, 더 이상 대기열에 없음, 보류할 수 없음, 보류 상태 아님, 재시도할 수 없음, 반려 상태 아님, 철회할 수 없음, 해제할 수 없음, 사유 필요, 또는 전송되지 않음(세부 정보 열 참조). 요약에는 "변경됨: n"과 "해당 상태에 적용할 수 없음: n."이 표시됩니다.

**7. 권한.** 열기: `screen:outbound-queue:open`. 재시도: `interface:outbound:resend`. 보류: `interface:outbound:hold`. 해제: `interface:outbound:release`. 보고 대상 아님으로 표시: `interface:outbound:mark-not-reportable`. 청구 철회: `interface:outbound:retract`. 지금 해제: `interface:outbound:override-release`. 모두 높은 위험도이며 감사 대상입니다. 재전송을 제외한 다섯 가지는 각각 화면 권한도 필요합니다. Admin이 이 모든 권한과 화면을 기본적으로 보유합니다. 검사실 책임자와 QA 검토자에게는 이 화면이 없습니다. 보류와 해제는 일괄 선택에 대해 한 번 확인됩니다.

**알려진 제한.** 대기열에는 PathScribe 측이 알고 있는 메시지가 들어 있습니다. 메시지가 수신자에게 도달했는지는 엔진의 수신 확인에 달려 있으며, 이는 예정 사항입니다. 현재는 2xx 응답이면 전송된 것으로 간주합니다. 수신 확인됨은 수신 확인을 전달하는 피드(등록기관)에만 나타납니다. 대상에 표시된 전송 방식은 레이블일 뿐이며, 전송은 엔진이 담당하기 때문입니다.

### 보고 피드 (Power BI) {#screen-bi_feed}
Breadcrumb: 홈 > 구성 > 시스템 > 통합 > 보고 피드 (Power BI)

**상태:** 부분 구현

**1. 탐색:** 구성 탭 **시스템** > 그룹 **통합**
**2. 유지 관리 항목:** 보고 피드 (Power BI)

**3. 업무 목적 및 범위.** Power BI, Excel, Tableau 또는 스크립트가 API 서버의 보고 API를 통해 PathScribe 데이터를 읽을 수 있게 합니다. 이들은 데이터베이스에 직접 연결하지 않습니다. 피드가 제공할 내용(데이터 집합과 수행 검사실 시설)을 선택하고, 도구마다 토큰을 하나씩 발급하며, 지정된 담당자가 승인하지 않은 한 식별 정보는 제외합니다. 기본적으로 토큰은 비식별 상태입니다. 이름, 기록 번호, 생년월일, 자유 텍스트는 제거되고, 날짜는 월 단위로 줄어들며, 90세 이상의 나이는 90+로 표시됩니다.

**무엇이 구현되어 있고 무엇이 아닌지.** 구현됨: 설정, 승인 기록, 토큰 생성·교체·폐기, 필드 목록, 가져오기 테스트. 토큰은 한 번만 표시되며, PathScribe는 지문만 보관하므로 다시 보여 줄 수 없습니다. 연결되지 않음: 피드 자체. 읽기 호출인 `GET /api/bi/v1/{dataset}`(`Authorization: Bearer psbi_...` 사용)은 문서로 작성된 계약이며 서버 작업 항목 PS-787입니다. 데모 빌드에서는 설정과 토큰이 브라우저에 보관되며, **가져오기 테스트**는 서버가 어떻게 응답할지를 시뮬레이션할 뿐입니다(행을 반환하지 않습니다). 배너가 이를 알려 줍니다.

**4. 사전 요건 및 종속성.** 토큰은 수행 검사실 역할이 있는 시설로만 제한할 수 있으므로 해당 시설이 먼저 필요합니다. 이를 건너뛰면 화면에 "설정된 수행 검사실 시설이 없습니다."라고 표시되며, 최소 한 개의 시설을 제공해야 하므로 토큰을 만들 수 없습니다.

### 요청서 수집 {#screen-requisition_ingestion}
Breadcrumb: 홈 > 구성 > 시스템 > 통합 > 요청서 수집

**상태:** 부분 구현

**1. 탐색:** 구성 탭 **시스템** > 그룹 **통합**
**2. 유지 관리 항목:** 요청서 수집

**3. 업무 목적 및 범위.** 종이 요청서는 부서 스캐너로 병원 네트워크 폴더나 타사 문서 시스템(ECM, LIS 문서 저장소, 스캔 서비스)에 일괄 스캔되거나, 다른 시스템이 PathScribe API로 보냅니다. 각 폴더나 시스템은 주소로 설정하는 하나의 출처이며 필요한 만큼 둘 수 있습니다. PathScribe는 각 페이지의 접수 바코드를 읽고 스캔을 증례에 참조로만 연결합니다. 증례에는 파일이 있는 위치로의 링크, 해당 페이지, 바코드, 시각, 출처가 남으며 PathScribe는 사본을 보관하지 않습니다. 바코드가 없는 페이지는 앞 요청서에 포함되고, 구분지는 요청서를 끝내며 어떤 증례에도 속하지 않습니다. 어떤 증례와도 매칭되지 않은 스캔은 접수 > **📥 요청서 수신함**의 미매칭 요청서 대기열에서 대기하며, 직원이 접수 번호를 스캔하거나 입력해 연결하거나 사유와 함께 폐기합니다.

**구현된 것과 구현되지 않은 것.** 구현됨: 이 설정, 매칭 및 페이지 묶음 규칙, 요청서 수신함, 보고서 화면의 증례 **📄 요청서** 버튼, 감사 기록. 데모 빌드에서는 누군가 **지금 실행**을 누르면 브라우저가 가상 PDF가 들어 있는 데모 폴더를 읽습니다. 구현되지 않음: 공유 폴더를 읽는 서버의 예약 작업(`requisition.ingest`), 바코드가 없을 때 인쇄된 번호 읽기(OCR), 전송 시스템이 스캔을 보내는 API. PDF만 읽으며 다른 파일은 거부되고 실행 요약에 표시됩니다.

**여러 수행 시설.** 각 출처는 하나의 수행 시설(**수행 시설** 필드)에 속하거나, 모든 검사실이 함께 쓰는 스캐너라면 **모든 시설**에 속합니다. 출처의 스캔은 해당 시설의 대기열에서 대기하며 아래의 모든 권한은 그 시설 기준으로 확인됩니다. 한 검사실에만 배정된 사람(직원 → 담당 시설)은 그 검사실의 스캐너와 스캔만 보고 실행하고 처리하며, 모든 시설에서 일하는 사람만 공용 출처를 추가하거나 변경할 수 있습니다. **＋ 출처 추가**로 스캐너를 더 추가하고, 양식 위의 버튼으로 전환합니다. 매칭은 기관 전체에서 이루어집니다. 접수 번호는 하나의 증례를 가리키므로 한 검사실에서 스캔한 요청서도 다른 검사실에서 수행하는 증례를 찾습니다.

**실행 방식(서버리스).** 각 출처는 한 배치를 처리하고 끝나는 예약 작업이 읽으며, PathScribe 클라우드에서 상시 실행되는 것은 없습니다. 타사 문서 시스템은 https 주소에서 읽고, 전송 시스템은 PathScribe API로 보냅니다. 병원 네트워크 폴더는 프린터와 공유 폴더용으로 이미 설치된 PathScribe **사이트 에이전트**([사이트 에이전트](#screen-site_agents))가 읽습니다. 에이전트가 병원 네트워크에서 바코드를 읽고 파일 참조, 페이지, 바코드만 PathScribe로 보내므로 PDF는 병원 밖으로 나가지 않습니다. 사이트 에이전트의 요청서 수집은 아직 구현되지 않았습니다. 요청서 누락 확인은 매시간 실행됩니다.

**4. 사전 요건 및 종속성.** 스캐너가 API 서버가 읽을 수 있는 폴더에 PDF를 저장하고(한 파일에 여러 요청서가 있을 수 있음), 요청서의 접수 라벨에 접수 번호가 Code 128 또는 Code 39 바코드로 있어야 합니다.

**미매칭 요청서 대기열(격리).** 바코드가 어떤 증례와도 맞지 않거나 읽을 수 없는 스캔은 자동으로 이곳에 들어갑니다(Requisition Quarantined). 직원은 **보기**로 페이지를 확인한 뒤 연결합니다. 접수 번호를 스캔하거나 입력하거나, 환자 이름 또는 MRN을 입력해 검색하거나(자신의 증례 접근 범위 내 **찾은 증례** 목록), **이 스캔으로 새 증례**를 눌러 스캔이 첨부된 접수 화면을 엽니다. 저장하면 새 증례에 연결됩니다(`case:accession:create` 필요). 모든 연결은 입력, 검색, 새 증례 중 어떤 방식인지와 함께 감사 기록됩니다(Requisition Re-associated).

**알려진 제한.** 인쇄용 구분지는 아직 없으므로 아무 라벨 도구로 바코드를 인쇄하십시오. 파일이 저장 위치에서 이동되거나 삭제되면 PathScribe가 사본을 보관하지 않으므로 증례의 요청서를 더 이상 열 수 없습니다.
