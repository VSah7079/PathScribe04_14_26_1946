# 시스템 개요 및 아키텍처 {#ch1}

이 장은 PathScribe 배포를 계획하는 관리자 또는 엔지니어를 위한 것입니다. PathScribe의 구성 요소가 무엇인지, 구성 요소 사이에서 데이터가 어떻게 이동하는지, 사이트가 무엇을 제공해야 하는지, 보안 통제가 무엇인지를 설명합니다. 이 장은 제품이 현재 수행하는 기능을 기술합니다. 구현되지 않은 것은 모두 **예정** 또는 **미구현**으로 표시하며, 가장 가까운 동작 기능이 어디에 있는지를 함께 안내합니다.

## 이 가이드 사용 방법 {#ch1-how-to-use}
Breadcrumb: 홈 > 관리자 가이드 > 시스템 개요 및 아키텍처 > 이 가이드 사용 방법

**상태:** 구현됨 (이 가이드와 앱의 **도움말** 버튼).

**각 장은 설정 순서를 따릅니다.** 2장은 1단계를, 3장은 2단계를 다루며, 이와 같이 7단계를 다루는 8장까지 이어집니다. N장은 N-1단계를 기술합니다. 사이트를 첫 장부터 마지막 장까지 순서대로 설정하면, 각 화면에 도달했을 때 그 화면이 의존하는 화면이 이미 설정되어 있습니다. 9장에는 부록(감사 로그 참조 및 용어집)이 있습니다.

**모든 화면에는 설정 순서 상자가 있습니다.** 이 가이드의 각 유지관리 화면에는 다음 세 줄이 있습니다.

- **Setup step:** 순서에서 그 화면의 위치이며, 예를 들어 "2단계, 6번째"입니다. 로그, 대기열 또는 일상적으로 사용하는 대시보드인 화면에는 "참조용이며 설정 과정에 포함되지 않음"이라고 표시됩니다.
- **Requires:** 먼저 설정해야 하는 화면입니다. 각 화면은 링크로 연결됩니다. 이를 건너뛰면 어떻게 되는지(빈 드롭다운 목록 또는 거부되는 저장)도 이 가이드에 설명되어 있습니다.
- **Unlocks:** 화면을 설정하고 나면 가능해지는 것입니다.

**설정 순서 마스터 페이지.** [설정 순서](setup-sequence.html)(`setup-sequence.html`)는 이 세 줄로 만들어지며, 모든 화면을 설정해야 하는 순서대로 나열합니다. 새 사이트의 점검표로 사용하십시오.

**도움말 버튼.** **구현됨.** **도움말** 버튼은 모든 설정 화면의 오른쪽 위에 있으며, 저장하지 않은 편집 내용이 사라지지 않도록 별도의 창(브라우저가 창을 거부하면 새 탭)에서, 위치를 기억하는 상태로 이 가이드의 해당 화면 섹션을 엽니다. 이 버튼은 열려 있는 탭과 사이드바 섹션을 따라갑니다. 직원 탭의 역할 사전에서는 [역할 사전](#screen-staff-roles) 섹션을 열고, **시스템 > 부서**에서는 [부서](#screen-departments)를 엽니다. 마이그레이션 작업 화면에는 제목 아래에 이 버튼이 있습니다. 이 버튼은 `go.html#<screen id>`를 여는데, `<screen id>`는 이 가이드에서의 화면 ID(예: `screen-departments`)이며, `go.html`은 가이드 빌드에서 생성되어 올바른 장 페이지를 찾아 줍니다. 설정 밖의 화면 중 이 가이드에 섹션이 있는 화면(감사 로그, 배치 관리, 락박스 접수 등)은 상단 표시줄의 마이크 옆에 있는 펼친 책 모양 버튼으로 엽니다. 설정 탭이나 섹션에 이 가이드의 섹션이 없으면 테스트가 실패하므로, 새 화면이 문서 없이 출시될 수 없습니다.

**상태 용어.** 모든 화면과 이 장의 모든 부분에는 고정된 다섯 가지 용어 중 하나를 사용합니다.

| 상태 | 의미 |
|---|---|
| **구현됨** | 데모 데이터에서 동작하며, 운영 서버를 위한 서비스 계약서(`docs/architecture/*_API.md`)가 작성되어 있습니다. |
| **데모** | 브라우저에서만 데모 데이터로 동작합니다. 운영 서버 측은 아직 연결되지 않았습니다. |
| **부분 구현** | 제목이 가리키는 내용의 일부가 구현되어 있습니다. 어느 부분인지는 해당 섹션에 정확히 나열되어 있습니다. |
| **예정** | 구현되지 않았습니다. 짧은 문단에서 의도하는 바와 시기에 관해 알려진 내용을 설명합니다. |
| **미구현** | 요청은 있었으나 화면이나 계약서가 없습니다. 해당 섹션에서 한 문장으로 이를 밝히고, 실제로 존재하는 가장 가까운 기능을 알려 줍니다. |

"구현됨"은 주의해서 읽으십시오. 브라우저 측이 동작하고 서버를 위한 계약서가 작성되어 있다는 뜻입니다. 운영 서버가 존재한다는 뜻은 아닙니다. 운영 서버의 현재 상태는 이 장의 다음 부분에서 설명합니다.

**FORMEDRIXAI INTERNAL ONLY.** 일부 설정은 ForMedrixAI의 배포 엔지니어 또는 서비스 엔지니어만 변경할 수 있습니다. `platform:` 도메인의 권한, `platformOnly`로 표시된 모든 권한, 그리고 해당 직원에게만 표시되는 화면이 이에 해당합니다. 이 가이드에서 해당 섹션의 제목은 `[FORMEDRIXAI INTERNAL ONLY]`로 시작하며, 섹션은 누가 그 설정을 변경할 수 있는지와 제한되는 이유를 알리는 상자 안내문으로 시작합니다. 고객용 가이드에는 이러한 섹션이 포함되지 않습니다. 내부용 가이드에는 포함됩니다. 고객 관리자이면서 ForMedrixAI 엔지니어가 언급하는 설정이 보이지 않는다면, 대개 이러한 설정 중 하나입니다.

## 요약 {#ch1-executive-summary}
Breadcrumb: 홈 > 관리자 가이드 > 시스템 개요 및 아키텍처 > 요약

**상태:** 부분 구현. 브라우저 애플리케이션은 구현되어 있습니다. 운영 API 서버, 데이터베이스 스키마 및 상시 가동 서비스는 문서화된 계약서로 명세되어 있으나 아직 구현되지 않았습니다([제품의 현재 상태](#ch1-current-state) 참조).

PathScribe는 ForMedrixAI LLC가 만든 AI 지원 임상 병리 보고 및 검사실 정보 시스템(LIS)입니다. 미국, 영국, EU 및 기타 시장을 대상으로 하며, 화면은 여섯 가지 언어(영어, 프랑스어, 독일어, 네덜란드어, 한국어, 스페인어)로 번역됩니다(영어 이외의 번역은 임상에서 사용하기 전에 원어민의 검토가 필요합니다).

케이스는 케이스별로 결정되는 두 가지 모드 중 하나로 진행됩니다.

- **CoPilot.** PathScribe는 호스트 LIS 위에서 동작하는 시놉틱 데이터 수집 계층입니다. 호스트 LIS가 케이스와 최종 보고서를 소유하고, PathScribe는 구조화된 시놉틱 데이터를 호스트 LIS로 되돌려 보냅니다.
- **Orchestration.** PathScribe가 AI 지원 서술문을 포함하여 케이스를 처음부터 끝까지 소유하는 경량 LIS로 동작합니다. 호스트 LIS가 없는 아웃리치 케이스에 사용합니다.

관리자가 통제하는 것은 구성입니다. 즉 직원과 역할, 사전과 조회 목록, 워크플로 규칙, AI 동작, 보고서 템플릿, 인터페이스 및 청구 규칙입니다. 이후의 장에서는 사이트를 설정하는 순서대로 이러한 화면을 기술합니다.

계획 수립에서 중요한 사실은 세 가지입니다.

1. **운영 데이터베이스는 Microsoft SQL Server입니다.** ASP.NET Core 기반의 PathScribe API 서버를 통해 접근하며, 실시간 업데이트는 SignalR로 처리합니다. PathScribe는 Firebase를 운영 데이터베이스로 사용하지 않습니다. 이전 작업에서 남은 일부 Firebase 파일이 저장소에 있으며, 교체될 예정입니다.
2. **호스팅은 고객 또는 ForMedrixAI가 선택합니다.** 설계는 표준 구성 요소(컨테이너, SQL Server, TLS 인증서)를 사용하며 특정 클라우드 공급자에 의존하지 않습니다. 사이트는 퍼블릭 클라우드, 프라이빗 클라우드 또는 소버린 클라우드, 또는 자체 데이터 센터를 사용할 수 있습니다.
3. **PathScribe는 아직 운영 환경에 배포할 수 없습니다.** 브라우저 애플리케이션은 시연하고 계약서를 기준으로 테스트할 수 있을 만큼 완성되어 있습니다. 실제 환자 데이터를 보관할 서버는 구현되지 않았습니다. 첫 배포는 설치가 아니라 ForMedrixAI와의 공동 프로젝트로 계획하십시오.

**상태:** 부분 구현. 아래 각 구성 요소에는 자체 상태가 있습니다.

### 구성 요소 {#ch1-parts}
Breadcrumb: 홈 > 관리자 가이드 > 시스템 개요 및 아키텍처 > 아키텍처 청사진 > 구성 요소

| 구성 요소 | 설명 | 상태 |
|---|---|---|
| **브라우저 애플리케이션** | 정적 파일로 제공되는 React 및 TypeScript 단일 페이지 애플리케이션입니다. 키를 보관하지 않으며, API 서버가 구성되어 있을 때는 환자 데이터를 브라우저 저장소에 기록하지 않습니다. 하나의 빌드가 모든 사이트에 사용되며, 각 사이트의 설정은 `index.html` 옆에 있는 `config.json` 파일에서 가져옵니다. | 구현됨 |
| **PathScribe API 서버** | ASP.NET Core입니다. 권한을 적용하고, 로그인 세션을 유지하며, 데이터베이스 트랜잭션과 예약 작업을 실행하고, AI 공급업체, 보고서 렌더러 및 인터페이스 엔진을 호출합니다. | 예정. 계약서는 `docs/architecture/*_API.md`에 작성되어 있습니다. 저장소에는 서버 코드가 없습니다. |
| **실시간 업데이트 허브** | API 서버의 `/hubs/live`에 있는 SignalR 허브입니다. 열려 있는 화면에 변경이 있음을 식별자만으로 알리며, 환자 텍스트는 전달하지 않습니다. | 예정. 브라우저 측은 구현되어 있으며 테스트용 허브로 테스트되었습니다. |
| **데이터베이스** | Microsoft SQL Server입니다. | 예정. 저장소에는 스키마나 스크립트가 없습니다. |
| **인터페이스 엔진** | Mirth Connect(Java 서버)의 오픈 소스 포크인 BridgeLink입니다. PathScribe가 JSON 메시지를 전달하면 엔진이 HL7을 만들어 전송하고 응답을 수신합니다. | 부분 구현. 메시지 계약서는 작성되어 있습니다. 엔진은 아직 배포되거나 연결되지 않았으며, 데모 빌드는 모의 엔진을 사용합니다. |
| **AI 프록시 및 AI 공급업체** | API 서버가 AI 요청을 구성된 공급업체로 전달하면서 공급업체 키를 추가하며, 브라우저는 이 키를 보유하지 않습니다. | 부분 구현. 브라우저 측과 관할권별 공급업체 확인은 구현되어 있습니다. 서버 경로는 예정입니다. |
| **보고서 렌더러** | Playwright로 제어하는 헤드리스 Chromium을 사용하여 발행된 보고서를 PDF로 변환하는 서비스입니다. | 예정. 개발용 대체 구성만 있습니다. |
| **사이트 에이전트** | 각 사이트에 설치되는 Windows 서비스입니다. HTTPS로 외부를 향해 연결하며, 보고서와 라벨을 네트워크 프린터로 인쇄하고 Windows 공유에 파일을 기록합니다. | 부분 구현. 관리 화면과 계약서는 구현되어 있습니다. 에이전트 자체는 예정입니다. |
| **워크스테이션 인쇄 브리지** | 작업대 컴퓨터에서 실행되어 옆에 있는 프린터로 라벨을 인쇄하는 QZ Tray 또는 PathScribe 워크스테이션 에이전트입니다. | QZ Tray: 구현됨(라벨이 이를 통해 인쇄됩니다). 워크스테이션 에이전트: 구현됨(브라우저 측). |
| **전체 슬라이드 영상(WSI) 뷰어** | 공급업체 자체의 뷰어 애플리케이션입니다(예: Leica, Roche 또는 Hamamatsu). PathScribe는 스캔 배치를 추적하고 해당 슬라이드의 공급업체 뷰어를 새 브라우저 탭에서 엽니다. 슬라이드 영상을 직접 그리지는 않습니다. | 구현됨(실행 링크). 스캔 배치 상태 업데이트에는 허브가 필요합니다. |

### 데이터 흐름 {#ch1-data-flow}
Breadcrumb: 홈 > 관리자 가이드 > 시스템 개요 및 아키텍처 > 아키텍처 청사진 > 데이터 흐름

```
 Hospital or lab network                         PathScribe hosting (cloud or on-premises)
 -----------------------                         ----------------------------------------
 Bench workstation                               Static web host (browser app, config.json)
   Browser app  --- https ---------------------> PathScribe API server (ASP.NET Core)
     |   ^                                         |        |         |          |
     |   +---- wss /hubs/live (SignalR) <----------+        |         |          |
     |                                                      |         |          |
     +-- QZ Tray / workstation agent (localhost)            v         v          v
         labels to the printer beside it                SQL Server   AI proxy   Report renderer
                                                         (database)    |        (Chromium PDF)
 Site agent (Windows service) --- https, outward ------>     |         v
   report and label printers, Windows shares                 |    AI vendors (per jurisdiction policy)
                                                             |
 Interface engine (BridgeLink) <---- JSON ---- API server ---+
   HL7 to and from the host LIS, EMR, instruments
   (hosted by ForMedrixAI, or installed at the hospital)
```

도식을 읽는 방법은 다음과 같습니다.

1. **브라우저에서 API 서버로.** 모든 작업은 로그인한 사용자의 ID로 API 서버를 거칩니다. 브라우저 자체의 권한 확인은 버튼을 숨길 뿐이며, 결정은 서버가 합니다. 서버는 고정된 오류 코드(`NOT_PERMITTED`, `NOT_FOUND`, `CONFLICT`, `INVALID`, `SIGNED_OUT`, `TOO_MANY_REQUESTS`, `TIMED_OUT`, `UNAVAILABLE`)를 반환하며, 환자를 특정할 수 있는 텍스트는 절대 돌려보내지 않습니다. 환자 이름과 식별자는 요청 본문으로 전달되며 웹 주소에는 절대 들어가지 않습니다.
2. **API 서버에서 허브를 거쳐 브라우저로.** 데이터베이스 변경이 커밋된 후 서버는 같은 트랜잭션 안에서 아웃박스 테이블에 이벤트를 기록합니다. 그런 다음 디스패처가 이를 허브를 통해 게시합니다. 이벤트에는 식별자만 담깁니다. 이를 수신한 화면은 권한이 확인되는 일반 호출로 데이터를 다시 읽습니다. 이를 처음 사용하는 화면은 수술실 라이브 보드(Live Board)와 수술중 대기열(Intraoperative Queue)이며, 설계 목표는 커밋에서 두 번째 보드까지 500밀리초 미만입니다. 허브가 없으면 같은 화면이 폴링합니다(수술중 화면에서는 15초마다).
3. **API 서버에서 AI로.** 브라우저는 자체 오리진의 `/api/ai/...`를 호출합니다. 서버는 공급업체 키를 추가하고, 관할권의 공급업체 및 지역 정책을 확인하고, 요청을 전달하며, 프롬프트 텍스트가 없는 감사 기록을 작성합니다.
4. **API 서버에서 인터페이스 엔진으로.** API 서버는 트랜잭션 유형이 포함된 JSON 봉투를 보냅니다(송신 유형 15가지가 `INTERFACE_TRANSACTIONS.md`에 나열되어 있습니다). 엔진은 이를 HL7로 매핑하여 전송합니다. PathScribe는 전송용 HL7을 직접 만들지 않습니다. HL7 트래픽은 PathScribe 메시지 버스가 아니라 엔진 자체의 메시지 저장소에 남습니다.
5. **API 서버에서 사이트 에이전트로.** 클라우드에서 호스팅되는 서버가 병원 내부의 프린터나 공유에 도달하는 유일한 방법은 사이트 에이전트입니다. 사이트 에이전트는 클라이언트 인증서를 사용하여 HTTPS로 서버에 외부 방향으로 연결하므로, 인바운드 방화벽을 열 필요가 없습니다.
6. **보고서.** 서버는 PathScribe를 떠나는 모든 PDF를 렌더링하고, 발행마다 변경할 수 없는 해시된 문서 한 건을 저장하며, 그 동일한 문서를 모든 채널로 보냅니다. 브라우저는 전송되는 내용과 일치하도록 만들어진 미리 보기를 표시합니다.

### 호스팅 및 규모 {#ch1-hosting}
Breadcrumb: 홈 > 관리자 가이드 > 시스템 개요 및 아키텍처 > 아키텍처 청사진 > 호스팅 및 규모

**상태:** 예정. 이것은 `DEPLOYMENT_READINESS_REVIEW.md`의 설계이며, 어느 것도 아직 배포된 적이 없습니다.

- **지원되는 두 가지 호스팅 방식.** 하나는 퍼블릭 클라우드이며, 적합한 경우 공급자의 관리형 데이터베이스와 컨테이너 호스팅을 사용합니다. 다른 하나는 이식 가능한 패키지로, 프라이빗 클라우드, 소버린 클라우드 또는 병원 자체 데이터 센터의 Kubernetes 또는 Docker에서 같은 컨테이너를 실행하는 방식입니다. 패키지는 한 번 검증되며, 이후 각 호스팅 위치에는 설치 적격성 평가(installation qualification) 점검표가 제공됩니다.
- **상시 가동 구성 요소.** API(최소 한 개의 웜 인스턴스), 데이터베이스(운영 환경에서는 자동 일시 중지 금지), 실시간 업데이트 허브, 보고서 렌더러, 그리고 HL7 연결을 유지하는 인터페이스 엔진입니다. 0으로 축소하는 방식은 1초 단위의 화면 새로 고침이나 야간의 STAT 케이스와 양립할 수 없습니다. 반복 작업(재시도, 발행 타이머, 만료 점검)은 짧은 예약 작업으로 실행할 수 있습니다.
- **허브 확장.** 공유 SaaS는 Azure SignalR Service를 사용합니다. 프라이빗 클라우드와 온프레미스는 Redis 백플레인 또는 단일 인스턴스를 사용합니다. Azure SignalR Service가 없으면 로드 밸런서에서 고정 세션(sticky session)과 WebSocket을 활성화해야 하며, 유휴 시간 제한은 15초보다 길어야 합니다. 개발 팀은 이 구성표를 아직 확인해야 합니다.
- **인터페이스 엔진은 어느 쪽이든 실행됩니다**(2026년 10월 13일 결정): 테넌트의 지역에서 ForMedrixAI가 호스팅하거나, 병원에 설치하며, 둘 다 동일한 컨테이너 이미지를 사용합니다.
- **하나의 빌드, 여러 사이트.** `npm run build:server`는 운영용 빌드를 만듭니다. 이 빌드에는 데모 계정이나 데모 도구가 포함되지 않습니다. 각 사이트의 주소와 로그인 설정은 `config.json`(설정 37개, `RUNTIME_SETTINGS`에 나열됨)에 넣으며, `Cache-Control: no-store`로 제공됩니다. 파일이 규칙을 위반하면(예: `https://`가 아닌 주소) PathScribe는 시작을 거부하고 잘못된 설정을 알려 줍니다.
- **브라우저 보안 헤더.** Content-Security-Policy, HSTS 및 기타 헤더는 `deploy/security-headers/`의 하나의 정의로부터 nginx, IIS 및 Azure App Service, Azure Static Web Apps, Azure Front Door용으로, 또는 단순 목록으로 생성됩니다. `config.json`의 주소를 변경한 후에는 새 주소가 허용되도록 생성기를 다시 실행하십시오.
- **스키마 변경**은 버전이 지정된 SQL 스크립트이며 릴리스 파이프라인이 적용하고, 애플리케이션 시작 시에는 절대 적용하지 않습니다. 각 변경은 이전 버전에서도 데이터베이스를 사용할 수 있는 상태로 남겨 둡니다.

## 제품의 현재 상태 {#ch1-current-state}
Breadcrumb: 홈 > 관리자 가이드 > 시스템 개요 및 아키텍처 > 제품의 현재 상태

**상태:** 거의 모든 데이터 화면이 데모입니다. 예외는 아래 표를 참조하십시오.

고객에게 가동 개시일을 약속하기 전에 이 부분을 읽으십시오. 이 내용은 2026년 10월 21일에 저장소를 기준으로 확인되었습니다.

**현재 실행되는 것.** 브라우저 애플리케이션은 **브라우저에 보관되는 데모 서비스**에서 실행됩니다. `src/services/`의 서비스 폴더 약 170개는 하나의 패턴을 따릅니다. 인터페이스, 데이터를 브라우저에 보관하는 데모 버전, 그리고(거의 모두에 대해) API를 호출하는 서버 버전입니다. 애플리케이션은 `config.json`에 `VITE_API_BASE_URL`이 설정되어 있으면 서버 버전을, 그렇지 않으면 데모 버전을 선택합니다. API 서버가 구성되어 있으면 데모 데이터는 메모리에 보관되며 브라우저 저장소에 기록되지 않습니다.

**운영 API에 연결된 것.** 없습니다. 서버 버전은 브라우저 코드에 있으며 모든 경로를 확인하는 가짜 서버 테스트가 있지만, 이에 응답할 API 서버는 저장소에 없고 구현되지 않았습니다(계약서를 바탕으로 인도 팀에 작업이 배정되어 있습니다). 실제 서버를 대상으로 시험한 적은 없습니다. 브라우저 코드의 서버 측 버전은 세 개의 서비스를 제외한 모든 서비스에 대해 작성되어 있습니다.

| 아직 서버 버전이 없는 서비스 | 이유 |
|---|---|
| 작업 레지스트리(음성 및 단축키 매칭) | 동기식이며 메모리에서 동작합니다. 저장된 설정만 구성 서비스를 통해 서버로 전달됩니다. |
| AI 지침 서비스 | 규칙이 주입된 저장소를 대상으로 브라우저에서 실행되며, 저장은 구성 서비스와 감사 서비스를 거칩니다. |
| 인터페이스 사전 서비스 | 마찬가지로 규칙이 브라우저에서 실행됩니다. 저장은 구성 서비스와 감사 서비스를 거칩니다. |

실시간 업데이트는 이미 브라우저에서 SignalR(`signalRLiveUpdateService.ts`)을 사용하지만, 허브는 구현되지 않았습니다.

**운영 배포를 막는 요인**(준비 상태 검토에서, Batch 641 시점의 상태):

| 차단 요인 | 상태 |
|---|---|
| API 서버 및 SQL Server 스키마 | 미해결. 시작되지 않았습니다. |
| 보고서 PDF, 내보내기 및 보류된 발행을 위한 Blob 저장소 | 계약서 작성됨. 저장소와 엔드포인트는 미해결입니다. |
| 서버 측 예약 작업(타이머 약 10개) | 미해결. 각 작업이 서버로 옮겨 가기 전까지는 누군가 로그인해 있는 동안 브라우저가 이를 실행합니다. `VITE_SERVER_JOBS`는 작업을 이름으로 서버에 넘깁니다. |
| 보고서 렌더러 서비스 | 세포병리 템플릿은 완료되었습니다. 호스팅 서비스는 미해결입니다. |
| 서버를 통한 로그인(backend-for-frontend), 런타임 ID 제공자 구성 | 런타임 구성은 완료되었습니다. 서버 부분은 미해결입니다. |
| 에지 규칙을 포함한 상시 가동 인터페이스 엔진 | 계약서 작성됨. 호스팅과 엔드포인트는 미해결입니다. |
| 사이트 에이전트 | 계약서와 화면은 완료되었습니다. 에이전트는 미해결입니다. |
| 허브 및 푸시 업데이트 | 브라우저 측은 완료되었습니다. 허브는 미해결입니다. |
| 이전의 Vercel `api/` 함수, Firebase 서비스 및 `functions/` 폐기 | 미해결. 세 개의 화면(각인기 모니터, QA 결함 목록, 재료 추적 이력)은 아직 Firebase 기반 서비스를 읽습니다. |

관리자가 알아 두어야 할 그 밖의 미해결 항목은 다음과 같습니다.

- **현재는 브라우저가 권한을 적용하며, 서버 측 적용은 구현되지 않았습니다.** 권한 확인은 브라우저의 서비스에서 실행됩니다. 실제 환자 데이터를 보관하기 전에 서버가 모든 확인을 반복해야 합니다. [보안 모델](#ch1-security)을 참조하십시오.
- **사람에 의한 화면 판독기 테스트는 수행되지 않았습니다.** 자동화된 접근성 검사(Chromium에서의 WCAG 2.1 A 및 AA 규칙)는 통과하지만, 사람이 NVDA 또는 VoiceOver로 테스트한 적은 아직 없습니다(PS-687).
- **Firefox는 빌드 작업 공간의 자동화 테스트 모음으로 실행하지 않았습니다.** Chrome, Edge 및 Firefox에서의 수동 확인은 미해결입니다(PS-718).
- **번역**(프랑스어, 독일어, 네덜란드어, 한국어, 스페인어)은 임상에서 사용하기 전에 원어민의 검토가 필요합니다.
- **지속적 통합 파이프라인**은 작성되어 있으나 저장소가 GitHub에 올라간 후에만 실행됩니다(2026년 10월 말 예정).

| 항목 | 저장소의 내용 |
|---|---|

| 컨테이너 플랫폼 | 이식 가능한 패키지에는 Kubernetes 또는 Docker, 퍼블릭 클라우드에는 공급자의 컨테이너 호스팅을 사용합니다. 버전: 아직 명세되지 않음. |
| 메시지 브로커 | 없음. 메시지 버스는 인터페이스(`IMessageBus`) 뒤에 있는 SQL Server 데이터베이스의 테이블입니다. RabbitMQ 또는 클라우드 큐는 부하 테스트에서 테이블이 병목으로 확인될 때만 추가합니다. |
| 빌드 도구(프런트 엔드를 빌드하는 엔지니어용) | Node.js 24.x(`package.json`의 `engines`). 정적 파일을 제공하는 운영 서버에는 필요하지 않습니다. |

### 데이터베이스 {#ch1-prereq-database}
Breadcrumb: 홈 > 관리자 가이드 > 시스템 개요 및 아키텍처 > 시스템 사전 요구 사항 > 데이터베이스

**상태:** 예정. 저장소에는 스키마, 스크립트 또는 데이터베이스 코드가 없습니다.

- **엔진.** Microsoft SQL Server입니다. 동일한 엔진이 Azure SQL Database(서버리스 또는 프로비저닝), 가상 머신의 SQL Server, Linux 컨테이너의 SQL Server(2017부터 2025까지의 Microsoft 공식 이미지, x86-64 Linux 호스트에서만, 라이선스 필요), 또는 AWS RDS for SQL Server로 실행됩니다.
- **운영 데이터베이스는 절대 자동 일시 중지하지 마십시오.** 일시 중지된 데이터베이스는 아침의 첫 화면이나 야간의 STAT 케이스를 실패한 요청으로 만듭니다. 자동 일시 중지는 테스트 및 교육용 테넌트에만 허용됩니다. Azure SQL 서버리스에서는 `-1`로 끕니다.
- **규모의 출발점.** 준비 상태 검토는 운영 테넌트에 대해 "부하 테스트에서 달리 판단할 때까지" 최소 가상 코어 2개를 권장합니다. 이것은 권장 사항이며 시험을 거친 요구 사항이 아닙니다. 저장소, 메모리, IOPS 및 케이스당 증가량: 아직 명세되지 않음.
- **스키마 변경.** 버전이 지정된 스크립트를 API 컨테이너가 시작되기 전에 릴리스 파이프라인이 적용하며, 애플리케이션 시작 시에는 절대 적용하지 않습니다.
- **백업.** 감사 테이블에 대해서는 특정 시점 복원이 설계입니다. 백업 일정, 보존 기간, 복구 시간 목표 및 복구 시점 목표: 아직 명세되지 않음.
- **AWS 참고.** AWS에는 서버리스 SQL Server가 없으며, 인스턴스 클래스를 변경하면 가동 중지가 발생합니다(다중 AZ로 단축됨). 라이선스 비용이 적용됩니다.
- 보고서 PDF, 내보내기 및 보류된 발행을 위한 **Blob 저장소**: Azure Blob 또는 S3 호환 저장소이며, 테넌트별로 비공개이고, 저장 시 암호화되며, 테넌트의 호스팅 지역에 둡니다(계약서: `BLOB_STORAGE_API.md`). PathScribe는 이미지나 첨부 파일을 저장하지 않으며, 검사실의 영상 시스템으로 연결되는 링크만 저장합니다.

### 네트워크 {#ch1-prereq-network}
Breadcrumb: 홈 > 관리자 가이드 > 시스템 개요 및 아키텍처 > 시스템 사전 요구 사항 > 네트워크

| 요구 | 세부 내용 |
|---|---|
| 모든 구간 TLS | `config.json`의 모든 서버 주소는 `https://`여야 합니다. 일반 `http://`는 개발 빌드에서 같은 컴퓨터로 가는 경우, 또는 보안 헤더 오리진 파일에 `"https": false`를 설정한 내부 배포(이 경우 HSTS가 제외됨)에만 허용됩니다. |
| 브라우저에서 API 및 허브로 | API 서버로는 HTTPS를 사용합니다. `/hubs/live`로는 WebSocket(`wss://`)을 사용합니다. 일부 병원 프록시가 WebSocket을 차단하므로 대체 수단으로 Server-Sent Events와 롱 폴링을 활성화한 채로 두십시오. 로드 밸런서에서는 WebSocket을 활성화해야 하며 유휴 시간 제한은 15초보다 길어야 합니다. |
| 허용되는 주소 | `config.json`의 주소(API, ID 제공자, 허브, 렌더러, 인터페이스 수신기, AI 및 용어 엔드포인트, 오류 모니터링)가 브라우저의 Content-Security-Policy가 됩니다. 변경 후에는 헤더 생성기를 다시 실행하십시오. |
| ID 제공자 | 브라우저에서(그리고 서버가 로그인을 담당하게 된 후에는 서버에서도) 접근할 수 있어야 합니다. Microsoft Entra ID의 리디렉션 주소: `https://<pathscribe host>/auth/callback/microsoft` 및 `https://<pathscribe host>/auth/signing/microsoft`. |
| 사이트 에이전트 | 외부 방향 HTTPS(포트 443)만 사용하며, 클라이언트 인증서를 요구하는 자체 호스트 이름(예: `agent.<tenant domain>`)을 사용합니다. 인바운드 방화벽 개방은 없습니다. TLS를 검사하는 프록시는 그 호스트를 변경 없이 통과시켜야 하며, 검사가 클라이언트 인증서를 깨뜨리기 때문입니다. |
| 사이트 에이전트 도달 범위(병원 IT가 현지에서 설정) | 프린터 서브넷, 프린터 포트(기본값 9100, 515, 631 및 443), 공유의 UNC 루트, 그리고 문서를 다운로드할 수 있는 호스트입니다. PathScribe는 이 목록을 변경할 수 없습니다. |
| HL7 연결 | 수신 오더와 송신 결과는 인터페이스 엔진을 사용합니다. 연결은 사이트 간 VPN 또는 TLS 기반 MLLP로 보호합니다. 메시지는 내구성 있게 저장된 후에만 확인 응답됩니다. |
| 고정 송신 주소 | SFTP 파일 전달에는 병원의 허용 목록을 위한 고정 송신 IP 주소(NAT 게이트웨이 또는 방화벽 송신)와 고정된 호스트 키가 필요합니다. |
| 팩스 및 이메일 | 인증을 사용하는 포트 587의 SMTP 게이트웨이입니다. |
| 대역폭 및 지연 시간 | 아직 명세되지 않음. 일반 화면 새로 고침의 설계 목표는 커밋에서 렌더링까지 95번째 백분위수에서 800 ms이며, 수술실 보드는 500 ms 미만입니다. 첫 페이지 로드는 압축 상태에서 0.70 MB입니다(목표 1 MB). |
| 호스팅 지역 | 배포마다 하나의 지역을 선택합니다. API 서버의 `/api/config`는 데이터베이스와 Blob 지역을 보고할 수 있으며, 이는 AI 동작 탭에 표시됩니다([AI 동작](#screen-tab-ai) 참조). 해당 엔드포인트는 예정입니다. |

### 클라이언트 워크스테이션 {#ch1-prereq-workstation}
Breadcrumb: 홈 > 관리자 가이드 > 시스템 개요 및 아키텍처 > 시스템 사전 요구 사항 > 클라이언트 워크스테이션

**상태:** 구현됨. 미해결 확인 사항이 있으며 아래에 기재되어 있습니다.

- **지원되는 브라우저**(2026년 10월 15일 결정): 최신 Chrome, Microsoft Edge 및 Firefox. **Safari는 지원되지 않습니다.** 자동화 테스트는 Chromium(Chrome과 Edge의 엔진)에서 실행됩니다. Firefox는 요청이 있을 때만 실행하며, 빌드 작업 공간에서는 아직 실행된 적이 없고, 세 브라우저 모두에서의 수동 확인은 미해결입니다(PS-718). Chrome과 Edge에서는 드롭다운 목록이 스타일이 적용된 패널로 그려지며, Firefox는 자체 목록을 표시합니다. 동작은 같습니다.
- **사용하는 브라우저 기능.** WebAssembly(맞춤법 검사기), Web Worker, 그리고(사용자가 허용한 경우) 카메라, 마이크 및 화면 캡처이며, 육안 검사 사진, 구술 입력, 개선 요청 스크린샷에 사용됩니다. Permissions-Policy 헤더는 이를 PathScribe에 대해서만 허용합니다.
- **작업대 컴퓨터에서의 라벨 인쇄.** QZ Tray(구현됨) 또는 PathScribe 워크스테이션 에이전트(구현됨, 브라우저 측)가 해당 컴퓨터에서 실행되어야 합니다. 이들은 해당 컴퓨터 자체에서만 수신 대기합니다. 워크스테이션 에이전트는 `wss://127.0.0.1` 포트 9100~9102에서, QZ Tray는 `localhost` 포트 8181, 8282, 8383 및 8484에서 대기합니다. 페이지가 QZ Tray에 도달하지 못하면 라벨은 브라우저의 인쇄 창에서 열리고, 라벨 프린터가 연결되어 있지 않다는 메시지가 표시됩니다.
- **로컬 네트워크 접근 허용.** Chrome과 Edge는 로컬 주소에 대해 사용자의 허락을 요청합니다. 병원 IT는 `LocalNetworkAccessAllowedForUrls` 정책으로 PathScribe를 미리 승인할 수 있습니다.
- **QZ Tray 확인 창.** 인쇄 요청이 고객의 인증서로 서명될 때까지 QZ Tray는 "이 웹사이트가 프린터를 사용하도록 허용하시겠습니까?"라고 묻습니다. 서명은 **예정**입니다(API 서버가 필요합니다). 그때까지는 워크스테이션마다 한 번씩 묻는 경우가 있을 수 있습니다. 결정 사항(2026년 10월 16일)은 고객당 자체 서명 인증서 하나이며, 이 인증서에는 IT가 갱신하고 다시 배포해야 하는 만료일이 있습니다. `docs/product/QZ_TRAY_CERTIFICATE_GUIDE.md`를 참조하십시오. 각 장치 관리 도구의 절차는 시험 운영 컴퓨터에서 실행된 적이 없으므로 "먼저 테스트"로 표시되어 있습니다.
- **라벨 프린터.** ZPL을 받는 감열 프린터입니다. 네트워크의 보고서 프린터는 사이트 에이전트를 통해 접근합니다. 네트워크 보고서 인쇄는 현재 브라우저에서는 동작하지 않습니다.
- **화면 판독기.** 자동화된 접근성 검사는 통과하며, NVDA 또는 VoiceOver를 사용한 사람의 테스트는 미해결입니다(PS-687).
- **언어.** 영어, 프랑스어, 독일어, 네덜란드어, 한국어, 스페인어이며, 벨기에 네덜란드어와 벨기에 프랑스어 표현이 추가됩니다.
- **모니터 크기, 최소 프로세서 및 메모리:** 아직 명세되지 않음.
- **전체 슬라이드 영상 뷰어.** 공급업체의 뷰어는 해당 공급업체가 요구하는 방식으로 워크스테이션에 설치되어 있거나 접근할 수 있어야 합니다. PathScribe는 뷰어마다 한 번 입력하는 실행 주소 템플릿에 슬라이드의 바코드를 채워 뷰어를 새 탭에서 열 뿐입니다. 이는 [공급업체 통합](#screen-vendor_integrations)에서 구성합니다. PathScribe는 뷰어 주소를 제공하지 않습니다.

## 보안 모델 {#ch1-security}
Breadcrumb: 홈 > 관리자 가이드 > 시스템 개요 및 아키텍처 > 보안 모델

**상태:** 부분 구현. 아래의 거의 모든 통제는 브라우저에 구현되어 있고 서버 계약서가 작성되어 있습니다. 각 확인을 반복해야 하는 서버는 구현되지 않았습니다([제품의 현재 상태](#ch1-current-state) 참조). 브라우저의 확인은 편의를 위한 것이며, 서버의 확인이 통제입니다. 서버 측이 존재하기 전에는 여기의 어떤 통제도 실제 환자 데이터를 보호한다고 설명하지 마십시오.

이 부분은 각 통제가 무엇을 하는지를 설명합니다. 이를 사용하면 검사실이 어떤 법률이나 표준을 준수하게 된다는 뜻은 아닙니다. 그것은 검사실 자체의 정책, 계약 및 품질 시스템이 결정합니다.

### 싱글 사인온 {#ch1-sso}
Breadcrumb: 홈 > 관리자 가이드 > 시스템 개요 및 아키텍처 > 보안 모델 > 싱글 사인온

**상태:** 부분 구현. OpenID Connect(OIDC): 브라우저 측은 구현됨. 서버 측은 예정.

- **프로토콜.** OpenID Connect이며, PKCE를 사용하는 인증 코드 흐름입니다. 앱은 공개 단일 페이지 애플리케이션 클라이언트(클라이언트 비밀 없음)로 등록됩니다. 범용이므로 Microsoft Entra ID, Okta, Ping 및 Keycloak에서 동작합니다. Microsoft Entra ID가 첫 번째 대상입니다. Entra 인증 기관은 테넌트를 지정해야 합니다. `/common`, `/organizations` 및 `/consumers`는 모든 Microsoft 계정의 접근을 허용하게 되므로 거부됩니다.
- **Google** 로그인은 제공되지 않습니다. Google의 토큰 엔드포인트가 클라이언트 비밀을 요구하기 때문입니다. Google Workspace를 사용하는 병원은 Entra ID 또는 Okta를 통해 Google을 연동할 수 있습니다.
- **로그인으로 계정이 생성되는 일은 없습니다.** 이미 프로비저닝되어 활성 상태인 직원만 로그인할 수 있습니다. ID는 이메일만으로가 아니라 제공자의 영구 주체(Entra의 `oid`, 없으면 `sub`)로 직원 기록과 대조됩니다. 첫 로그인에서는 이메일을 신뢰할 수 있는 경우(검증되었거나 테넌트 전용 Entra 인증 기관인 경우) 이메일로 연결할 수 있으며, 설정으로 이를 끄면 관리자가 각 계정을 연결합니다. 거부(프로비저닝되지 않음, 비활성, 모호함, 이미 연결됨, 애플리케이션 접근 권한 없음)는 평이한 메시지로 표시되고 감사됩니다. [직원](#screen-staff-members)을 참조하십시오.
- **데모 빌드**는 비밀번호 로그인도 제공합니다. 운영 빌드(`VITE_AUTH_MODE`를 `sso`로 설정)에는 데모 계정이 없습니다.
- **토큰.** 현재 브라우저가 토큰을 `sessionStorage`에 보관합니다(이 탭에서만, 탭을 닫으면 사라짐). **운영 환경에서는 예정**(2026년 10월 3일 및 10월 15일 결정): API 서버가 토큰을 보관하고, 브라우저는 위조 방지 헤더가 있는 `HttpOnly`, `Secure`, `SameSite` 세션 쿠키만 받습니다. 브라우저는 JWT를 전혀 지니지 않으며, 허브도 같은 쿠키를 사용합니다. 이를 위해서는 서버에 공유 세션 저장소(SQL Server 또는 Redis)가 필요합니다.
- **Entra ID에 앱 등록**(`AUTHENTICATION_OIDC.md`에 따른 병원 IT용 절차): 플랫폼은 단일 페이지 애플리케이션이고 [네트워크](#ch1-prereq-network)에 나열된 두 리디렉션 주소를 사용하는 단일 테넌트 등록, 클라이언트 비밀 없음, ID 토큰의 선택적 `email` 클레임, 그리고 애플리케이션에 부여된 노출 API 범위입니다.
- **디렉터리의 계정과 역할.** 자동 계정 동기화(SCIM: 입사자, 변경 및 퇴사자)는 서버 단계에서 **예정**입니다. 디렉터리 그룹을 PathScribe 역할에 매핑하는 기능은 첫 릴리스 이후에 **예정**입니다. 도입되면 그룹은 작업대 역할만 부여할 수 있고, Admin, 검사실 책임자, 템플릿 승인자 또는 서명 권한이 있는 역할은 절대 부여할 수 없으며, 각 매핑에는 두 번째 관리자의 승인이 필요합니다. 현재는 역할을 [직원](#screen-staff-members)과 [역할](#screen-staff-roles)에서 수동으로 부여합니다.

#### SAML 2.0 {#ch1-saml}
Breadcrumb: 홈 > 관리자 가이드 > 시스템 개요 및 아키텍처 > 보안 모델 > 싱글 사인온 > SAML 2.0

**상태:** 미구현.

PathScribe에는 SAML 2.0 로그인, SAML 라이브러리 및 SAML 화면이 없습니다. 저장소 전체를 검색하면 이 단어는 두 개의 설계 문서에서만 발견됩니다. 실제로 동작하는 가장 가까운 기능은 위의 OIDC입니다. 공유 SaaS 호스팅에 대해 문서화된 방향은 병원이 PathScribe ID 브로커(Microsoft Entra ID External ID)를 통해 로그인하는 것이며, 이 브로커는 병원 디렉터리와는 SAML 또는 OIDC로, PathScribe와는 일반 OIDC로 통신하므로 "PathScribe는 SAML을 직접 처리하지 않습니다". 해당 브로커는 **예정**이며 구현되지 않았습니다. 프라이빗 클라우드 또는 전용 배포는 병원 자체의 Entra ID에 OIDC로 직접 연결합니다. 현재 SAML만 제공할 수 있는 병원은 계획 단계에서 ForMedrixAI에 이를 알리거나, SAML을 Entra ID 또는 Okta에 연동하십시오. 그러면 이들이 PathScribe와 OIDC로 통신합니다.

### 역할 기반 접근 제어 {#ch1-rbac}
Breadcrumb: 홈 > 관리자 가이드 > 시스템 개요 및 아키텍처 > 보안 모델 > 역할 기반 접근 제어

**상태:** 데모. 확인은 브라우저의 서비스에서 실행됩니다. 서버 측 적용(`AUTHORIZATION_API.md`, 4단계)은 **예정**입니다.

- **권한.** PathScribe가 적용하는 모든 것은 `domain:object:verb` 형식으로 이름 붙인 권한이며, 예를 들어 `config:retention-policy:manage`입니다. 카탈로그(`capabilityCatalog.ts`)가 유일한 목록이며 약 320개의 권한이 있습니다(작성 시점 322개이며, 릴리스마다 숫자가 늘어납니다). 권한은 그 확인과 함께일 때만 추가되며, 확인이 없는 권한이 있으면 테스트가 빌드를 실패시킵니다. 각 권한에는 위험 수준이 있습니다. **고위험** 권한에 대해서는 작업에서 이루어지는 모든 확인이 허용되었든 거부되었든 감사 로그에 기록되며, 모든 내보내기는 고위험입니다.
- **역할.** 역할은 권한의 집합입니다. 직원 한 명은 하나 이상의 역할과 시설 배정을 가집니다(배정이 비어 있으면 모든 시설을 뜻합니다). 범위는 역할이 아니라 배정에 속합니다. 확인은 보유한 역할이 권한을 부여하고, 그 권한이 요구하는 모든 권한도 부여되며, 작업이 해당 사람의 시설 범위 안에 있을 때만 통과합니다. 거부에는 사유가 제시됩니다(부여되지 않음, 요구 사항이 부여되지 않음, 범위 밖, 시설을 알 수 없음).
- **기본 제공 역할.** 열여섯 가지입니다. 병리의, 전공의, 펠로우, 병리 보조사, Admin, 의사, 수술실 직원, 템플릿 작성자, 템플릿 승인자, 검사실 책임자, QA 검토자, 접수 담당자, 조직기술사, 세포병리사, 분자 기술사 및 Superadmin입니다. 의사와 수술실 직원은 애플리케이션 접근 권한이 없는 디렉터리 항목입니다. 초기값은 최소 권한을 따릅니다. 병리의는 기본적으로 구성 권한을 갖지 않습니다. 관리자는 Superadmin을 제외하고 [역할](#screen-staff-roles)에서 역할을 변경하고 추가할 수 있습니다.
- **어떤 역할에도 우회는 없습니다.** Superadmin은 다른 역할과 마찬가지로 권한을 부여받는 역할이며, 확인에 이를 위한 지름길은 없습니다. Admin도 아무것도 암시하지 않습니다. Superadmin은 `config:ai-prompt:approve`(AI 지침 승인)를 제외한 모든 권한을 보유합니다. 이 권한은 업무 분리를 위해 부여하지 않으므로, 검사실 자체의 AI에 전달되는 내용은 검사실(검사실 책임자)만 승인하며 ForMedrixAI 지원 담당자는 승인하지 않습니다.
- **Superadmin은 ForMedrixAI 지원 전용입니다.** 지원용 로그인을 통해서만 보유됩니다. 병원은 이를 배정하거나 편집하거나 직원 역할 선택기에서 볼 수 없으며, 이를 지정한 직원 기록은 그로부터 아무것도 얻지 못합니다. 그 ID의 서버 측 출처(ForMedrixAI 자체의 ID 테넌트)는 **예정**입니다.
- **플랫폼 전용 권한.** `platform:` 도메인의 권한 여섯 개는 Superadmin에게서만 유효합니다(테넌트 간 케이스 보기, 관리 기관, 서명 규칙, 그리고 인터페이스 사전의 관리, 게시 및 시뮬레이션). 병원 역할은 이를 보유할 수 없습니다. 해당 화면은 이 가이드에서 `[FORMEDRIXAI INTERNAL ONLY]`로 표시됩니다.
- **테넌트 경계.** 모든 사용자와 케이스에는 `organisationId`가 있습니다. 테넌트 간 접근은 지원 접근(아래)으로 제한됩니다. 현재는 브라우저에서 적용하며, 이를 적용하는 서버 측 쿼리 계층은 예정입니다.
- **케이스 비공개.** 케이스를 열 수 없는 사람은 존재하지 않는 케이스와 동일한 중립적인 메시지를 받습니다. 입력하거나 붙여 넣은 접수번호는 아무것도 증명하지 않으며, 메시지는 읽는 사람이 해당 케이스를 열 수 있을 때만 번호를 링크로 바꿉니다. 서버는 "그런 케이스 없음"과 "볼 수 없음"에 대해 본문, 헤더 또는 소요 시간에 차이 없이 같은 응답(예: `404`)을 주어야 합니다.
- **화면.** 각 화면에는 고유한 `screen:<name>:open` 권한이 있습니다. 홈과 허브는 사용자가 열 수 있는 타일만 표시하며, 경로에서 다시 확인합니다.
- **음성 및 키보드 명령**은 접근 제어가 아니며 접근 권한을 부여하는 데 사용되지 않습니다.
- **관리하는 위치.** [역할](#screen-staff-roles), [직원](#screen-staff-members) 및 [직원 탭](#screen-tab-staff). 역할과 권한의 변경은 감사됩니다.

### 다단계 인증 및 서명 시 재인증 {#ch1-mfa}
Breadcrumb: 홈 > 관리자 가이드 > 시스템 개요 및 아키텍처 > 보안 모델 > 다단계 인증 및 서명 시 재인증

**상태:** 부분 구현. 브라우저 측은 구현됨. 데모 계정의 인증기는 **시뮬레이션**입니다. 서버 측은 예정.

- **싱글 사인온 사용자.** 두 번째 요소는 ID 제공자가 요청합니다. PathScribe는 ID 토큰을 읽고, `amr`에 `mfa`가 포함되어 있거나, 서로 다른 두 계열(지식, 소유, 고유 특성)의 방식이 지정되어 있거나, `acr`이 다단계 등급을 지정하면 MFA로 인정합니다. 비밀번호만으로는 MFA가 아닙니다. 조직이 MFA를 요구하는데 토큰에 그렇게 표시되어 있지 않으면, 평이한 메시지와 함께 로그인이 거부됩니다. 제공자는 이러한 클레임을 보내도록 설정되어 있어야 합니다(Entra: MFA를 요구하는 조건부 액세스 정책, Okta: 소유 요소가 있는 인증 정책, Keycloak: 인증 수준을 `acr`에 매핑하고 `amr` 매퍼를 추가).
- **조직별 정책.** [세션 보안](#screen-session_security)에서 설정합니다. 요청 대상(없음, 보고서에 서명하는 역할, 또는 모든 사람, 기본값은 없음), 서명에 새 코드가 필요해지기까지의 시간(1~720분, 기본값 30), 두 번째 요소가 만료되어 세션이 종료되기까지의 시간(1~72시간, 기본값 12)입니다. `config:session-security:manage`로 저장되며 감사됩니다.
- **서명 시 단계 상향.** 마지막 두 번째 요소가 단계 상향 시간보다 오래되었으면 서명 시 다시 요청합니다. 비밀번호 세션에서는 새 코드를, 또는 제공자에서의 새 로그인(`prompt=login`)을 요구하며, 그 토큰은 다시 MFA를 단언해야 합니다.
- **데모 계정.** 복구 코드가 한 번만 표시되는 **시뮬레이션** 시간 기반 인증기(RFC 6238)입니다. 데모 빌드에만 있습니다. 서버 빌드에는 시뮬레이션 요소가 없으므로, 싱글 사인온을 사용하지 않으면서 MFA를 요청받은 사용자는 사용할 수 없다는 안내를 받고 로그인할 수 없습니다. 등록 재설정에는 `auth:mfa-enrolment:reset`이 필요합니다.
- **잠금.** 코드를 다섯 번 틀리면 확인이 15분간 잠깁니다. 비밀번호 로그인을 다섯 번 실패하면 이메일이 15분간 잠깁니다. 이 횟수는 현재 브라우저에 보관되며, 서버가 이를 보관해야 합니다. 싱글 사인온에서는 제공자가 자체 잠금을 적용합니다.
- **서명 시 인증 정책**(구현됨, 데모). 수행 시설별로, 서명할 때마다 비밀번호를 입력하거나(기본값, `strict`) 세션당 한 번 입력하며(`session`, 길이 15, 30, 60 또는 240분), 선택적으로 두 번째 요소를 사용할 수 있습니다. 세션은 시간 초과, 로그아웃 또는 역할 변경 시 종료됩니다. 세션당 한 번 방식은 이후 서명에 대해 21 CFR Part 11(11.200(a)(1))이 기대하는 바에서 벗어난다고 화면이 경고하므로, 고객의 품질 시스템이 결정합니다.
- **생체 인식 서명**(WebAuthn, Touch ID 또는 Windows Hello)은 선택적 확인입니다. 각 사용자가 자신의 장치를 등록하며, 비밀번호도 항상 사용할 수 있습니다. 생체 인식 호출의 서버 버전은 작성되어 있으나 화면은 아직 이를 사용하지 않습니다.
- **미구현:** 네트워크에 의한 원격 로그아웃 제한, 서명 세션의 워크스테이션 잠금 만료, SMS 및 하드웨어 키 두 번째 요소, 서버 측 정책 저장소.
- **관리하는 위치.** [세션 보안](#screen-session_security).
### 세션 보안 {#ch1-session}
Breadcrumb: 홈 > 관리자 가이드 > 시스템 개요 및 아키텍처 > 보안 모델 > 세션 보안

**상태:** 부분 구현. 유휴 시간 제한은 구현됨(브라우저). 서버가 보관하는 세션은 예정.

- **유휴 시간 제한.** [세션 보안](#screen-session_security)의 조직 전체 기본값이며 5, 10, 15, 20, 30 또는 60분 중에서 선택합니다. 기본값은 15입니다. 수행 검사실은 [시설 사전](#screen-facility-dictionary)에서 자체 값을 설정할 수 있습니다. 케이스가 열려 있을 때는 검사실의 값이 적용되고, 그 밖의 곳(홈, 작업 목록)에서는 조직의 값이 적용됩니다. 시간이 초과되면 사용자는 로그아웃되며, 저장하지 않은 초안은 삭제되지 않고 보존됩니다.
- **같은 계정, 두 번째 탭.** 다른 탭에서 같은 사용자로 다시 로그인하면 안내 메시지와 함께 같은 브라우저의 이전 세션을 대체합니다.
- **서버 규칙.** 서버는 토큰이 만료된 세션도 종료하므로, 닫혔거나 멈춘 브라우저가 세션을 계속 열어 둘 수 없습니다.
- **브라우저 저장소.** API 서버가 구성되어 있으면 환자 데이터는 브라우저 저장소에 기록되지 않습니다. 표시 환경설정, 워크스테이션 설정(스캔 스테이션, 디스플레이 프로필, 창 위치) 및 로그인 세션만 브라우저 저장소를 사용합니다.
- **전송 및 페이지 보호.** 생성되는 헤더는 엄격한 Content-Security-Policy(인라인 스크립트, `eval`, 프레임 삽입 모두 없음), https 배포에서의 HSTS, `nosniff`, `no-referrer` 정책(주소에 케이스 ID가 포함될 수 있음) 및 제한된 Permissions-Policy를 설정합니다. 보고서 HTML은 표시되기 전에 정화됩니다. 브라우저는 AI, 용어 또는 공급업체 키를 보유하지 않으며, 프런트 엔드에 키가 나타나면 테스트가 빌드를 실패시킵니다.
- **오류 보고서.** 충돌 보고서는 Sentry 또는 병원 자체 수집기로 보낼 수 있으며 **기본적으로 꺼져 있습니다**. 보고서에는 오류 이름, 정화된 메시지(인용된 텍스트, 이메일 주소, 세 자리 이상 연속된 숫자 없음), 최대 열 개의 스택 프레임, 숫자 구간이 대체된 경로, 그리고 참조 번호만 담깁니다. 이를 사용하려면 `config.json`에 두 가지 설정이 필요하며, 미국 고객은 제공자와 서명된 업무 제휴 계약(BAA)이, EU와 영국은 데이터 처리 계약과 EU 데이터 상주가 필요합니다. 자체 호스팅하면 둘 다 피할 수 있습니다.
- **관리하는 위치.** [세션 보안](#screen-session_security) 및 [시설 사전](#screen-facility-dictionary).

### 지원 접근 {#ch1-support}
Breadcrumb: 홈 > 관리자 가이드 > 시스템 개요 및 아키텍처 > 보안 모델 > 지원 접근

**상태:** 부분 구현. 브라우저 측은 구현됨. 서버 측은 예정.

데이터 관리자인 병원이 ForMedrixAI 지원 담당자가 병원의 데이터에 접근할 수 있는지를 결정합니다. "지원 접근"은 Superadmin 세션이 해당 사용자가 직원이 아닌 조직에 접근하는 것을 뜻합니다.

- **조직별 정책.** 사용 안 함(지원 담당자는 Superadmin을 포함하여 아무것도 얻지 못함), **승인 필요**(기본값) 또는 항상 허용입니다. 승인 필요에서는 지원 담당자가 티켓마다 10자 이상의 사유와 함께 요청합니다. 병원의 승인자(요청자가 아님)가 승인하거나 거부합니다. 승인은 조직의 접근 기간(30분, 1, 2, 4 또는 8시간이며 기본값은 2) 동안, 또는 지원 담당자가 종료하거나 병원이 취소하면 그보다 짧게 유지됩니다.
- **병원 자체의 감사 스트림.** 주 감사 로그와는 별개입니다. 요청, 결정, 만료, 거부된 열람 시도, 케이스 열람과 편집, 케이스를 노출한 모든 목록 또는 검색(케이스 ID, 검색 조건의 이름이며 값은 절대 포함하지 않음), 정책 변경 및 내보내기가 기록됩니다. 각 항목은 이전 항목과 해시로 연결되어 있어 항목이 변경되거나 제거되면 연결이 끊어지며, 화면에 변조 확인이 표시됩니다. 내보내기는 CSV 또는 JSON입니다.
- **권한.** `config:support-access:policy`, `config:support-access:approve` 및 `config:support-audit:view`이며, Admin에 초기 부여됩니다. 다른 조직의 케이스를 열려면 Superadmin만 보유할 수 있는 `platform:cross-tenant-cases:view`도 필요하며, 이는 감사됩니다.
- **미구현(서버 작업):** 발신 IP 주소와 국가(브라우저는 이를 빈 값으로 기록함), 승인자에 대한 이메일 및 웹훅 알림(현재는 앱 내 메시지), 티켓이 종료될 때 접근 종료, 스트림의 PDF 내보내기(CSV와 JSON은 있으며, PDF 함수는 브라우저에 작성되어 있음), 테넌트별 자체 추가 전용 테이블에 있는 스트림, 그리고 티켓과 만료에 묶인 지원 세션 토큰입니다.
- **관리하는 위치.** [지원 접근](#screen-support_access).

### 감사 로그 기록 {#ch1-audit}
Breadcrumb: 홈 > 관리자 가이드 > 시스템 개요 및 아키텍처 > 보안 모델 > 감사 로그 기록

**상태:** 부분 구현. 브라우저 측은 구현됨. 서버 저장소는 예정.

- **기록되는 것.** 사용자 작업, 로그아웃, 정정, 음성 이벤트, 시스템 이벤트 및 AI 호출입니다. 모든 고위험 권한 확인은 허용되었든 거부되었든 기록됩니다. 권한 있는 사람이 수행한 구성 변경은 감사됩니다. 일부는 이전 값과 새 값을 기록하지만(예: AI 공급업체 정책과 서명 권한 재정의), 많은 설정에 대해 로그에는 새 값이 아니라 권한 확인이 허용되었다는 항목만 담깁니다. 각 항목에 담기는 내용은 [시스템 로그](#screen-audit-log)를 참조하십시오.
- **상세 내용에는 환자 데이터가 없습니다.** 감사 `detail` 텍스트는 영어 그대로이며 환자 이름, 생년월일, MRN 또는 임상 수치를 담지 않도록 만들어집니다. 식별자와 구성 이름을 사용합니다. 비밀번호, 코드 및 비밀 정보는 절대 기록되지 않습니다.
- **서버 설계.** 추가 전용 테이블(삽입 및 선택 권한만 부여), 기록하는 변경과 같은 트랜잭션에서 작성되는 각 감사 행, 지원 접근을 위한 해시 연결 스트림, 그리고 특정 시점 백업입니다. 변경할 수 없는 저장소에 내보낸 감사 보관본은 병원별 선택 사항입니다. **예정:** 서버가 구현되기 전에는 아무것도 존재하지 않습니다. 브라우저 버전은 로그를 데모 저장소에 보관합니다.
- **보존.** [데이터 보존](#ch1-retention)을 참조하십시오.
- **확인하는 위치.** [시스템 로그](#screen-audit-log)이며, 인터페이스 및 재무 보기는 [시스템 로그: 인터페이스](#screen-audit-interfaces)와 [시스템 로그: 재무](#screen-audit-financial)입니다.

### 지원용 스크린샷에서 환자 데이터 가리기 {#ch1-phi}
Breadcrumb: 홈 > 관리자 가이드 > 시스템 개요 및 아키텍처 > 보안 모델 > 지원용 스크린샷에서 환자 데이터 가리기

**상태:** 구현됨.

사용자가 개선 요청을 보내면, 앱은 스크린샷을 찍고 이미지가 브라우저를 떠나기 전에 환자 데이터로 태그된 모든 요소를 가립니다. 환자 이름, 생년월일, MRN 또는 국가 식별자, 접수번호 또는 케이스 번호, 환자 연락처 또는 보험 정보를 표시하는 모든 요소에는 그 종류와 함께 `data-phi`가 태그됩니다. 케이스를 언급하는 토스트 알림도 함께 가려지도록 감쌉니다. 직원 이름은 환자 데이터로 취급하지 않습니다. 테스트가 모든 소스 파일을 읽고 태그되지 않은 곳이 있으면 예외 목록 없이 빌드를 실패시킵니다. 계획 시 고려할 한계는 다음과 같습니다. 식별자가 우연히 포함된 자유 텍스트(감사 상세, 인터페이스 예외 사유)는 어떤 코드 검사로도 인식할 수 없으므로 해당 셀은 통째로 가립니다. 그리고 검사는 유형이 아니라 이름을 읽으므로, 일반 목록을 통해 전달된 값은 놓칠 수 있습니다(그러한 사례가 Batch 368에서 발견되어 수정되었으며, 이후 브라우저에서 스무 개 화면을 확인했습니다).

### AI 공급업체 정책 및 호스팅 지역 {#ch1-ai-policy}
Breadcrumb: 홈 > 관리자 가이드 > 시스템 개요 및 아키텍처 > 보안 모델 > AI 공급업체 정책 및 호스팅 지역

**상태:** 부분 구현. 브라우저 확인은 구현됨. 서버 프록시 확인은 예정.

- **이유.** 일부 관할권은 허용되거나 금지되는 AI 공급업체를 지정합니다. PathScribe는 공급업체에 중립적이며 모든 AI 호출을 보내기 전에 확인합니다.
- **규칙.** 관할권별로, 그리고 선택적으로 시설별로 허용되는 AI 서비스와 각 서비스에 대해 허용되는 호스팅 지역을 정합니다. 규칙이 없으면 모든 서비스가 허용됩니다. 시설 규칙은 해당 관할권의 규칙을 좁히며, 호출은 둘 다 통과해야 합니다. 규칙이 지역을 제한하는 경우 지역이 기록되지 않은 호출은 거부됩니다. 서비스는 요청 형태로 지칭합니다. 구조화된 메시지(Anthropic), 채팅 완성(OpenAI), 관리형 채팅 완성(Azure OpenAI), 모델 게이트웨이(AWS Bedrock), 구조화된 콘텐츠(Google Gemini) 및 사용자 지정(자체 호스팅 모델)입니다. 구성된 호스팅 지역은 AI 제공자 설정과 함께 저장됩니다.
- **거부되는 경우.** 기능은 AI 없이 계속 진행되며, 가능한 곳에서는 "이 관할권에서는 AI를 사용할 수 없습니다"라고 알립니다. 호출이 대신 다른 공급업체로 전송되는 일은 없습니다.
- **서버는 확인을 반복해야 합니다.** 브라우저 확인은 우회될 수 있으므로, 서버의 AI 프록시가 모든 경로에서 같은 확인을 수행해야 하며 결정적인 것은 서버의 확인입니다. 서버는 요청 본문이 아니라 저장된 설정에서 서비스와 지역을 선택해야 하고, 코드 `AI_VENDOR_NOT_ALLOWED`와 함께 `403`으로 응답하며, 거부를 감사해야 합니다. **예정.**
- **키.** 브라우저는 AI 공급업체 키를 보유하지 않습니다. 운영 환경에서 키는 서버의 비밀 저장소(예: Azure Key Vault)에 있습니다. 저장된 설정에는 제공자, 모델, 엔드포인트 및 배포 이름이 담기며 키는 절대 담기지 않습니다.
- **서버가 추가로 수행해야 하는 것(예정):** 각 AI 호출 감사(누가, 케이스, 확인한 시설과 관할권, 서비스, 모델, 호스팅 지역, 기능, 토큰, 결과이며, 환자 데이터를 담을 수 있는 프롬프트는 절대 포함하지 않음), 사용자 및 조직별 속도 제한, 그리고 선택한 제공자에 대해 업무 제휴 계약 또는 데이터 처리 계약이 체결되어 있는지 확인하는 것입니다.
- **공개된 격차.** 브라우저에서 제공자 설정이 `mock`이면 AI 요청이 프록시를 통해 Anthropic 경로로 전송되므로, `mock`으로 설정된 데모 사이트도 프록시를 호출합니다. Anthropic을 허용하지 않는 관할권은 이를 거부합니다.
- **사람의 검토.** AI 출력은 제안입니다. 이를 사용하는 화면은 임상의가 수락하거나 거부하도록 표시합니다. AI 장(5장)을 참조하십시오.
- **관리하는 위치.** [AI 동작](#screen-tab-ai) 탭의 AI 공급업체 정책 카드와 호스팅 지역 카드입니다. 규칙을 변경하려면 `config:ai-vendor-policy:manage`(기본적으로 Admin과 검사실 책임자)가 필요하며, 각 변경은 `AI_VENDOR_POLICY_CHANGED`로 감사됩니다.

### 데이터 보존 {#ch1-retention}
Breadcrumb: 홈 > 관리자 가이드 > 시스템 개요 및 아키텍처 > 보안 모델 > 데이터 보존

**상태:** 부분 구현. 설정은 구현되어 있습니다. **현재는 이 설정에 따라 데이터를 삭제하는 것이 없습니다.** 삭제 작업은 서버 작업입니다.

[데이터 보존](#screen-retention)에는 네 가지 기간이 있습니다. AI 제안(기본값 90일), 감사 로그(기본값 365일), 케이스 스냅샷(기본값 7년), 보고서 보관소(기본값 10년)입니다. 화면은 감사 로그의 최소 보존 기간이 90일이며, 규제상의 최소 기간 미만으로 줄이려면 기관의 규정 준수 책임자의 승인이 필요하다고 경고합니다. 저장하려면 `config:retention-policy:manage`가 필요합니다. 실제 검체와 블록의 보존은 폐기 대기열과 케이스 수준의 보존 보류가 처리하며, 이는 관할권(영국은 RCPath, 미국은 CAP과 CLIA)을 따릅니다. Blob 저장소의 변경할 수 없는 보고서 문서는 그 자체로 삭제에 대한 보호입니다. 백업의 보존 기간: 아직 명세되지 않음.

### HIPAA 및 CLIA: 제품이 갖춘 통제 {#ch1-regulatory}
Breadcrumb: 홈 > 관리자 가이드 > 시스템 개요 및 아키텍처 > 보안 모델 > HIPAA 및 CLIA: 제품이 갖춘 통제

**상태:** 부분 구현. 표에는 브라우저 빌드에 존재하는 통제가 나열되어 있습니다. 서버 측이 존재하기 전에는 어떤 통제도 실제 환자 데이터를 보호하지 않으며, 이러한 통제를 사용한다고 해서 검사실이 HIPAA, CLIA 또는 다른 어떤 법률을 **준수하게 되는 것은 아닙니다**. 준수 여부는 검사실의 정책, 계약, 호스팅 및 품질 시스템에 달려 있습니다.

| 영역 | PathScribe가 갖춘 것 | 상태 | 위치 |
|---|---|---|---|
